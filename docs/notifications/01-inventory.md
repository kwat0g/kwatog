# Notification and badge inventory, leak analysis, root causes

**Audit date:** 2026-10-25
**Evidence:** static source review plus aggregate-only queries against local development database.
**At discovery baseline:** no notification or badge code changed. Later remediations and verification state are tracked in `PROGRESS.md`.

## Coverage and confidence

`00-discovery.md` contains full module/status discovery, all 73 internal sidebar destinations, 19 portal destinations, nine compact-shell destinations, and 32 backend badge definitions after PR #388. This report cross-references that inventory and lists every one of the 129 `NotificationService` call sites with its event-type expression and immediate audience expression. Mail-only Laravel notifications, custom alert email, payroll payslip mail, digest, and failure-wrapper paths appear in the separate-path register below.

Static source coverage is complete for the inspected repository. Runtime recipient-to-role delivery, authorization outcomes, badge/list parity, and frontend visual behavior are **not verified**. No seeded-user scenario, test suite, browser session, or production query ran during discovery. A source expression such as `$audience` identifies the value passed to the service; its construction remains in the cited caller and is not a runtime recipient trace. Follow-up PR #370 centralizes the seven mail-only Laravel notification sends listed below; it preserves their explicit recipient selection and does not add policy-based resolution or record-access checks. PR #414 later adds an invoice subject gate to selected accounting notifications and invoice email-failure fallbacks; remaining event families are not gated.

No public broadcast channel or literal “notify every user” dispatch was found. Current exposure risk comes from broad permission/role-derived or caller-built collections that lack a shared subject-access gate, not from an observed public notification stream. Do not read local role/type aggregates as proof that a recipient was correct or incorrect.

## Root causes

1. **Notification dispatch has no shared recipient contract.** The principal service receives completed arrays and trusts caller. Permission lookup does not automatically mean record access, ownership, department/site scope, or current responsibility.
2. **Record authorization is caller-specific.** Approval action notices use the approval registry and source scope; many other sends do not call a common policy gate. There is no stored selection reason or safe audited fallback.
3. **Audience construction is fragmented.** 129 sites pass 129 event arguments and caller-built recipient values. Portal account scoping, role/permission queries, assignees, and explicit user IDs coexist; actors are not excluded centrally.
4. **Badges and destination lists have separate query definitions.** Definitions are per-key closures, nav items attach at most one key, and neither the badge registry nor shared list scopes prove parity.
5. **Badge visibility metadata can drift.** Frontend nav gates and backend badge permission gates differ in at least three candidates; only selected role tests exist.
6. **Route and display behavior are decentralized.** Links and copy live in caller payloads. Bell click is not an anchor; no `link_to` produces no destination. Event types absent from the catalog/metadata lose intended preference/category rendering.
7. **Realtime authorization is mixed.** Notification and badge channels are private and user-scoped/empty refresh respectively. Other subject channels often authorize by permission only without loading the requested scoped record.
8. **There is no proven public-channel leak.** Search found no public data channel and no literal notification-to-all-users query. Known broad selectors include pricing notices to every active user with a module permission. Custom approval sweeps include active system administrators only when they hold the candidate approval permission, then filter read permission and candidate-specific rules; PR #454 adds the final subject-access gate. Runtime role scenarios remain incomplete.
9. **Some source selectors are broader than the passed business rule.** `PricingReviewService::notify()` accepts a role list but ignores it, using only the selected permission. The former custom-escalation administrator fanout was removed under F-17; remaining custom approval scope needs per-kind dispatch verification.
10. **Some outcomes send even when link access fails.** Several services set `link_to` to `null` for a requester without the relevant view permission but still send the notification. This violates the approved-app-access condition unless a separate requester-safe access policy is proven.

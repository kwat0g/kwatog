# Separate-track findings

**Date:** 2026-10-26
**Status:** Audit observations. Draft recipient fixes for F-21 and F-22 are tracked in PR #333; other findings remain separate. Recipient changes follow the approved policy.

| ID | Severity | Finding | Evidence / certainty | Separate fix direction |
| --- | --- | --- | --- | --- |
| F-01 | High | `profile_requests` badge appears on Employees instead of Bank Account Changes/Profile Update Requests. | Confirmed in `spa/src/components/layout/Sidebar.tsx`; destination `/hr/profile-update-requests` has no badge. | Move attachment and verify its permission/filter parity in isolated PR. |
| F-02 | High | Approval badge counts pending approval rows by role/delegate without applying approval source visibility. | Confirmed in `BadgeService`; approval board uses `ApprovalSourceScope`. Parity and hidden-count impact not runtime-tested. | Share the approval queue scope with badge query; add positive/negative tests per role/source. |
| F-03 | High | Purchase-request badge counts own role only; active delegates and source visibility are not included. | Confirmed in `BadgeService`; approval resolver has active delegates and source-view filtering. | Use shared current-step PR scope; compare badge with filtered list. |
| F-04 | Medium-high | Badge permission declarations differ from sidebar route declarations for Payroll, Complaints, and Deliveries. | Confirmed string mismatch: `payroll.view` vs `payroll.periods.view`; `crm.complaints.manage` vs `crm.complaints.view`; `supply_chain.view` vs route's `supply_chain.view OR supply_chain.deliveries.view`. Runtime role impact untested. | Align registry visibility with backend route/list authorization; test role overrides and feature flags. |
| F-05 | Medium | Seven badge definitions are not attached to any sidebar item: `training_expiry`, `training_upcoming`, `open_postings`, `inquiries`, `mrb_holds`, `shipments`, `pending_transfers`. | Confirmed by comparing `BadgeService` keys with `Sidebar.tsx`. | Attach only to a matching authorized list/filter, or remove unused definition in a separate cleanup PR. |
| F-06 | Medium | Some emitted internal event types lack exact catalog entries: `supplier.shipment_late`, `quality.late_incoming`, and dynamic `production.rework.*`. | Static exact-string scan found no backend preference entries. `supplier.shipment_late` matches a broad Logistics frontend rule; `quality.late_incoming` and `production.rework.*` fall back to generic System metadata. | Add reviewed type metadata/template entries with valid routes; classify every dynamic state. |
| F-07 | Medium | Employee-targeted `training.expiry` rows have no `link_to`; staff-targeted rows link to `/hr/employees/{hash}`. | Confirmed in `TrainingExpiryService`. A click on the employee's own notification has no destination. | Add a self-service training route only after confirming it exists and grants the employee access; otherwise render a safe no-link state. |
| F-08 | Medium | Notification row click uses a button + SPA navigation; it is not a real anchor. | Confirmed in Bell and Center components. Middle-click/open-in-new-tab is unavailable. | Use accessible anchors with mark-read behavior and forbidden/deleted route fallback. |
| F-09 | Medium-high | Sidebar badge counts and destination list queries are separate implementations; parity tests were not found. | Static inspection; no role/list scenarios run. | Extract shared scopes, then prove count equals filtered total per role/scope before enabling each signal. |
| F-10 | Medium | Alert unread count counts global unresolved, non-dismissed rows with `is_read=false`; it is not per-user, and the default alert list includes all unresolved/non-dismissed rows regardless of `is_read`. | Confirmed in `AlertController`; the badge/count cannot equal the default list total. Product meaning of alerts as shared vs personal remains open. | Label separately as shared open-alert count and give it a matching filtered list, or add an explicit per-user recipient/read model. |
| F-11 | Medium | Reverb notification event broadcasts full notification envelope rather than only an identifier. | Confirmed in `UserNotificationCreated`; current channel is private and bound to one user. | F-12 | Medium-high | Several private subject channels authorize by permission without record-specific scope checks. Payroll progress event includes run metadata/headcount. | Confirmed in `routes/channels.php` and event payload; current negative coverage is limited. This is a channel-access risk, not a proven unauthorized subscription. | Load subject and use same policy/scope as corresponding record endpoint; test unauthorized and cross-scope subscriptions. |
| F-13 | Medium | Current one-count nav badges hide signal meaning and link to broad module pages. | Confirmed in current sidebar and badge service. | Replace only after signal scope and destination filter are shared and approved. |
| F-14 | Low-medium | `training.expiry` link and notification message reveal employee/training details to its recipient set; exact staff scope needs review. | Payload and resolver are visible in `TrainingExpiryService`; recipient resolution includes owner, configured department heads and HR staff with scope checks, but no seeded-user run. | Keep details minimal and verify employee/department boundary through negative recipient tests. |
| F-15 | High | Four in-app notification calls omit `link_to`; queue-long-wait plus three permission-override notices. | Confirmed by the exhaustive payload register in `01-inventory.md`. | Add a verified authorized route or a clear no-link message; do not point restricted users at inaccessible records. |
| F-16 | High | Several decision notices still deliver to requester when code only nulls an inaccessible link. | Confirmed patterns in `ApprovalService::notifySubmitter`, `BudgetService`, `BudgetTransferService`, `BillService`, `InvoiceService`, and `StockAdjustmentService`; runtime access outcome untested. | Apply the approved subject-view gate before delivery, or define a requester-safe summary route whose policy proves access. |
| F-17 | High | Custom approval escalation merges every active `system_admin` into recipients after scoped approvers are resolved. | Confirmed in `CustomApprovalEscalationService`; added admins are not rechecked with `ApprovalTypeRegistry::userCanViewRecord`. Whether system-admin policy can open each source record remains untested. | Remove implicit system-admin fanout or require explicit source-view policy and approved escalation rule. |
| F-18 | High | Pricing notification audience ignores the passed role list and selects every active user with the chosen permission. | Confirmed in `PricingReviewService::notify`; cached active-user collection is filtered only by `hasPermission`, with no product/customer assignment scope. | Resolve the intended reviewer/record owner with product/account scope; preserve only approved escalation roles. |
| F-19 | Medium | Dashboard regularization count and employee self-service derive due dates from different fields/rules. | `DashboardWidgetDataService::probationSummary()` filters `employees.date_regularized`; `SelfServiceController` derives `expected_regularization_date` from hire date and `hr.probation.period_months`. The intended authority is unverified. | Ask HR to name authoritative field/rule; do not use the count as a badge until dashboard, employee list, and self-service share it. |
| F-20 | Medium-high | Sales-order confirmation notice uses a configured role list plus `production.schedule.view`, carries no order identifier, and links to the general schedule page. | Confirmed in `NotifyOnSalesOrderConfirmed::handle`; no per-order visibility/scope check or record deep link appears in this call. Whether configured planning users are intended as a company-wide audience is untested. | Notify only the planning owner with schedule access and scoped order visibility; include a verified order/plan target, or classify as a content-free schedule refresh. |
| F-21 | Medium-high; partial recipient fix in draft PR [#333](https://github.com/kwat0g/kwatog/pull/333) | Core approval notices could reach a role holder who can view the subject but lacks the action permission enforced by its API route. Active role delegates can also be blocked by routes using direct `permission:` middleware. | `ApprovalNotificationRecipientResolver` checked source view access only; `CheckPermission` checks the user's own action permission, while `ApprovalService::userMayActFor()` separately accepts active role delegations. The draft now requires the step's route permission before sending. `return_management.approve` negative coverage checks a viewable user with a revoked action permission and a viewable delegate without that permission. | Keep notifications limited to users the current route allows to act. Track delegated-action route alignment separately; change that behavior only after verifying each route's record scope and adding route-level positive/negative tests. |
| F-22 | Medium; recipient fix in draft PR [#333](https://github.com/kwat0g/kwatog/pull/333) | A PO approver granted `purchasing.po.approve` by user override can open a PO detail through the route and policy, but the notification resolver required `purchasing.view` and dropped that approver. | Confirmed in `Purchasing/routes.php`, `PurchaseOrderAccessPolicy::visibleTo()`, and `ApprovalTypeRegistry::userCanViewRecord()`. The draft registry now records the route's alternative view permission and adds a resolver regression test; CI is pending. | Keep each approval type's notification visibility permissions aligned with its detail route and source policy. |

These findings are not merged into notification/badge implementation work. No claim of a confirmed cross-user leak is made without runtime evidence.

# Pricing, supplier cost, BOM and automation cross-module audit

Audited October 4, 2026. Scope: the recently added pricing requests, Finance approval, customer acceptance, supplier cost reviews, BOM refresh, notifications and runtime-health handoffs. This is a focused audit, not a complete review of Sales, Purchasing, Quality or Accounting.

No application, role, runtime or live business data was changed during this audit. Eight isolated probes reproduced the behaviors below: eight tests, 22 assertions. A passing probe means the gap was reproduced; it does not mean the behavior is safe. The previous successful E2E checks cover the normal flow but do not cover these conditions.

Implementation follow-up: all twelve findings were addressed in the [hardening record](pricing-cross-module-hardening.md). The table below preserves the original audit evidence. Its probe asserts historical unsafe behavior; use the desired-behavior regression suite linked in the hardening record for current validation.

## Findings

| ID | Severity | Gap and concrete consequence | Evidence | Smallest correction |
| --- | --- | --- | --- | --- |
| PA-01 | High | Finance approval has no expected proposal version or reviewed-cost signature. Finance can load version 1 at 30.00, Sales submits version 2 at 16.00, and Finance's original approval approves version 2. The current floor check does not prove Finance approved the terms it saw. | Reproduced through HTTP. `PriceNegotiationService.php:84`, `PriceNegotiationRequest.php:40`, `pricingRequests.ts:16`. | Send the displayed version and cost signature; compare under the existing transaction lock before approval. | PA-02 | High | Pricing review ignores the linked finished-goods Inventory item's standard cost. A product configured at 10.00 with matching Inventory cost 100.00 and no BOM is considered complete at 10.00; Finance can approve a 30.00 offer. Supplier approval can update Inventory without updating the cost basis used by pricing. | Reproduced. `PriceNegotiationService.php:242`; supplier updates `ItemService` through `ItemCostReviewService.php:56`. | Reuse the established product-to-item mapping and base-unit checks. Include the approved mapped cost in financial review and its signature. Distinguish purchased goods from manufactured goods before treating a missing BOM as complete. |
| PA-03 | High | Product management permission can change product standard cost and minimum selling price without Finance cost authority. The real PPC role lacks `inventory.costs.approve` but can reduce product cost and floor to 1.00. The Inventory cost-approval control therefore does not govern all financial cost/floor writers. | Reproduced through the PPC HTTP endpoint. `ProductService.php:100`, `UpdateProductRequest.php:18`, `RolePermissionSeeder.php:795`. | Separate product-maintenance rights from financial cost/floor changes at the shared service boundary. PPC can propose changes; Finance authorizes the financial values. |
| PA-04 | Medium | An offer starting today cannot be accepted tomorrow, even when its end date is still a month away. Approval and acceptance reuse the creation rule requiring the start date to be today or later. The offer remains `offered`, while its acceptance button fails. | Reproduced with time travel. `PriceNegotiationService.php:215`. | Validate future start dates when proposing; validate the agreed acceptance window when reviewing/responding. Preserve dates and any required commercial policy rather than silently changing them. |
| PA-05 | Medium | Sales can propose a restricted product to an unassigned customer and Finance can approve it. Customer sees the offer but acceptance fails because product access is checked only at acceptance. Agreement creation's assignment hook executes too late to rescue the offer. | Reproduced. `PriceNegotiationService.php:55`, `:140`; `PriceAgreement.php:37`. | Verify portal availability before offering. Require an explicit assignment through existing product access when necessary, then recheck at acceptance. |
| PA-06 | Medium | Stale supplier reviews are safely refused, but there is no usable renewal path for that receipt. After rejection, capture returns the same rejected review with the old cost because the receipt line is unique forever. Archiving an item also blocks rejection because the service resolves only an unarchived Item before checking the decision. | Stale-review renewal reproduced. Archive rejection follows `ItemCostReviewService.php:33`. `capture()` at `:18`. | Preserve review history while creating a new review revision or explicitly reopening with the corrected source snapshot. Permit rejection/closure of archived-source reviews; keep approval eligibility strict. |
| PA-07 | Medium | Supplier cost review UI is inside the CRM feature guard, while its API and navigation belong to Inventory. With Inventory enabled and CRM disabled, an authorized Finance/PPC/Purchasing user can read the API but cannot reach the review page. | Static route/guard proof: `crmRoutes.tsx:40`, `:69`; `Inventory/routes.php:24`; Sidebar supplier-cost entry uses `feature: inventory`. | Put the page under Inventory's feature guard and keep its existing review/approve permissions. |
| PA-08 | Medium | Existing Finance installations and fresh seeds have different read rights. The migration grants approval but omits `crm.price_agreements.view`; the seeder grants both. Live Finance has approval but no agreement view. Finance can review requests but receives 403 on the underlying agreement list, and cannot inspect accepted terms through that page. | Live read-only permission check; `2026_10_04_000005_add_pricing_negotiation_and_cost_reviews.php:50` vs `RolePermissionSeeder.php:561`. | Apply an additive, targeted read grant consistent with the approved role policy. Do not reseed all roles and overwrite custom grants. |
| PA-09 | Medium | Notification recipients depend on canonical role slugs, not the people actually authorized to perform the handoff. A custom Finance role with the approval permission receives no proposal alert. Revoked permissions do not remove a canonical role from the audience. Withdrawal/expiration also lack a notification and portal-visible reason. | Custom approver omission reproduced. `PriceNegotiationService.php:261`, `:176`, `:194`; `PriceRequestResource.php:23` hides history from the customer. | Select active recipients by the relevant permission, retain permission-aware links, and expose a customer-safe decision reason. | PA-10 | Medium | Operations Health can report `healthy` with a two-day-old, repeatedly attempted pricing outbox row. It displays a count but neither age nor failed attempts affects status. A healthy scheduler does not prove the queue worker or BOM handoff succeeds. | Reproduced with a successful scheduler tick and an old pending row. `RolloutHealthService.php:65`. | Include overdue pending/processing age and the existing failure evidence. Reuse queue monitoring; avoid a second scheduler/health framework. |
| PA-11 | Medium | A BOM business-rule refusal is caught, leaves `costed_at` null and produces a notice, but the pricing outbox can be published successfully. Health only counts failed outbox rows, so an unresolved BOM costing failure is absent from its automation status. Daily review retries the estimate, but does not make the failure visible in that health summary. | Static process proof: `PricingReviewService.php:56`; `RolloutHealthService.php:67`. | Count stale/refused active estimates in health and link to the existing PPC correction surface. | PA-12 | Medium | Open requests do not protect product identity or archival. Before the first agreement/order/BOM exists, the product may change part number/base unit or be archived while a request is open. Offer records read the live product, so the customer sees changing identity and may be unable to finish. | Static dependency proof: `ProductService.php:108`, `:228`; `PriceRequestResource.php:16`. Neither identity nor archive dependency checks includes open pricing requests. | Add open negotiations to existing product dependency guards, or close affected requests explicitly with a recorded reason. |

## Boundaries verified

- Customer lists explicitly filter by customer ID; acceptance checks ownership before and after locking. The existing HTTP test blocks a different customer. No confirmed cross-customer disclosure was found in the current pricing endpoints.
- Customer resources omit internal manufacturing cost, Finance review details, offer-state signature and staff history. Current endpoint families keep staff and portal guards separate.
- Customer consent remains mandatory; repeated acceptance creates one agreement. Product/customer locks and the unique open-pair index protect the normal request path.
- Supplier decisions enforce Finance authority. Receipt eligibility, positive accepted quantity, changed source cost and changed standard cost guards prevent unsafe approval.
- Existing orders retain saved prices. A dated accepted replacement changes future pricing without rewriting the old agreement's unit prices.
- Live scheduler and queue services are active; scheduler health reports success. No pending or failed pricing outbox rows were present during live read-only checks. PA-10 and PA-11 describe failure-mode visibility, not a current live outage.

## Reproduction

The probe is [PricingCrossModuleAuditProbeTest.php](probes/PricingCrossModuleAuditProbeTest.php). It deliberately asserts the observed gaps and should be converted to desired-behavior regression tests when fixes are authorized.

Use only the dedicated isolated database:

```bash
docker cp docs/testing/probes/PricingCrossModuleAuditProbeTest.php ogami-api:/tmp/PricingCrossModuleAuditProbeTest.php
docker exec ogami-api php vendor/bin/phpunit -c phpunit.pricing.20261004.xml /tmp/PricingCrossModuleAuditProbeTest.php
```

The configuration targets `ogami_test_pricing_20261004`; the probe uses `RefreshDatabase`. Never run it with a production database configuration.

Recommended order: PA-01 approval fencing, PA-02/PA-03 financial cost ownership, PA-04/PA-05/PA-06 blocked handoffs, PA-07/PA-08/PA-09 access and notifications, PA-10/PA-11 visibility, PA-12 product dependency protection. All corrections can reuse the current services, guards, notifications, transactions and review pages.

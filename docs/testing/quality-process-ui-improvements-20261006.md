# Quality inspection process and interface improvements

Review date: 6 October 2026. Scope: all five QC inspection stages, their specification and source connections, inspection list, manual creation, detail, review, and recovery handoff. This is an audit and recommendation; no product changes were applied.

Evidence includes the completed [five-stage verification](quality-all-stages-20261006.md), current source inspection, fresh read-only Chromium captures at 1440 px and 390 px, and a real filtered defect-Pareto API probe. Business data in the screenshots belongs to the isolated audit application. The deterministic Impeccable scan returned no findings for `spa/src/pages/quality/inspections`; it does not establish workflow correctness or accessibility compliance.

## Recommended order

1. Correct misleading workflow and quantities, preserve unfinished work, and resolve the two errors already reproduced during testing.
2. Make the checklist compact and bring its primary action into view, retaining the established Atelier design and all important record information.
3. Add small, safe conveniences through existing filters, dialogs, saved draft endpoints, and notification mechanisms.

## Process findings

| Priority | Finding and evidence | Recommended smallest change |
| --- | --- | --- |
| P1 | **Failed inspection hides the existing recovery record.** A real failed outgoing inspection has one NCR, but its detail page neither renders an NCR link nor explains the disposition. It instead offers `Report defect`, which is appropriate for a new late incident but confusing for an existing failure. | Expose the linked NCR, current disposition, and release state. Show `Open NCR` for the existing unresolved incident. Keep `Report another defect` for a genuinely separate late incident, following existing service rules. Use the viewer's NCR permissions. |
| P1 | **QC result and warehouse acceptance use the same label for different quantities.** A passed incoming record shows `Accepted quantity: 0`, while its linked GRN is already `Accepted` with source quantity `125.500 KG`. `finalizeTerminal()` populates inspection accepted quantity only for outgoing. | Label outgoing capacity as `Approved for release`; show incoming warehouse acceptance from the exact GRN line in its original unit. Until that data is present, display the receipt status rather than a misleading zero. Do not infer warehouse acceptance from a PASS alone. |
| P1 | **PASS/FAIL defects disappear from failure charts.** A real outgoing inspection contains three failed requirements, but the filtered Pareto API includes only `Fit check`. `DefectParetoService` queries only `is_pass = false`; attribute decisions use `item_result = failed` and leave `is_pass` null. | Select failures according to capture method in the shared analytics query and drill-down. Label chart totals as failed checks or occurrences, separately from unique defective pieces. Count a row once, even if both evidence fields indicate failure. Include return stages in frontend filter types and preserve cancelled/history exclusions. |
| P1 | **Unfinished checklist work lacks navigation protection.** Decisions and readings exist in component state; unlike creation and specification forms, the checklist does not use the existing unsaved-changes guard. A reload before `Save draft` discards work. The draft request also excludes physical count and batch-only problem fields. | First reuse the existing navigation guard and show `Unsaved changes` or `Draft saved`. Preserve draft decisions/readings through the existing endpoint. If adding automatic saves, debounce only valid drafts, scope recovery by user, inspection, and result version, and never save or restore coverage confirmation as an attestation. Saving the remaining draft fields needs an explicit backend contract. |
| P1 | **Closed-WO recovery policy conflicts across callers.** The delayed completion listener and missing-QC sweep accept closed WOs, while their shared creation service rejects the source. This reproduced in the backend suite. | Keep ordinary closure and late-defect safeguards. Make missing-QC recovery explicitly escalate for controlled reconciliation, or add a narrowly authorized historical recovery path with its own provenance. Do not remove the closed-source guard merely to make the test pass. |
| P1 | **Transient throttling can look like session expiry.** The previous real-browser test received a 429, then displayed a session-expired sign-in screen. Authentication bootstrap clears identity for every error. | Separate unauthorized sessions from temporary network/server/throttle failures. Show retry guidance and honor `Retry-After`; never assume temporary failure means logout. Never render protected data before authentication is established. |
| P2 | **Manual creation offers stages without their real source.** The form submits stage, product, quantity and an outgoing output ID; it cannot select the exact GRN or return line for other source-linked stages. The service safely refuses release from standalone evidence, but users can still confuse a diagnostic record with chain QC. | Make source-created inspection the default entry route. Keep manual inspection clearly labeled `Standalone inspection` when no source is selected. Direct incoming and return users to their receipt/return records; show missing automatic handoffs with an actionable repair message. |
| P2 | **Sampling guidance does not match actual capture.** Manual outgoing creation displays AQL code, Ac and Re, but checklist outgoing creation requires full piece coverage and every check to pass. The options endpoint describes in-process as full inspection, while actual in-process creation uses a bounded sample. Incoming saved plans may also say AQL although checklist PCS capture overrides to full coverage. | Return and display the actual stage/capture coverage policy. Show `Inspect all 100 pieces` for outgoing PCS, `Inspect the planned sample` for in-process, and `Inspect this lot` for bulk material. Keep AQL terminology only for historical measurement flows that use it. |

## Page improvements

| Priority | Current issue | Proposed interface |
| --- | --- | --- |
| P1 | **Checklist appears too far down.** Fresh captures place it about 779–827 px from the top on desktop and 1270–1300 px on mobile. Details and linked records precede the actual inspection task. | Keep record flow at the top, as previously requested. Put a compact details summary directly above the checklist. Keep linked records and full history in the desktop side column; place them after the checklist on mobile. Retain all important details, with no required details dropdown. |
| P2 | **Every requirement consumes a tall section.** References, method, target, both limits, controls, and helpers repeat. Terminal records still look like disabled entry forms. | Use a compact desktop checklist table: `Check`, `PASS requirement`, `Actual size`, `Result`. Reveal a problem field below failed rows only. Use stacked touch-friendly rows on mobile. Display finalized results as readable text and result chips, with full-contrast actual readings and problem descriptions. |
| P2 | **Completion and blockers are hard to scan.** Only the first blocker is shown near the bottom; action buttons require substantial scrolling on long specifications. | Add `4 of 5 checks completed · 1 failed` near the checklist title. Reuse the existing attention filter and add a jump to the first unanswered or invalid check. Use a sticky action row inside the existing content shell, keeping controls clear of the mobile header and keyboard. Errors should identify the check and unit, not only a generic missing-size message. |
| P2 | **List emphasizes historical counts over pending work.** Cards count only the current 25 rows, and there is no `Awaiting review` card. Search cannot find a WO, GRN, return number, or output batch. Bulk rows show `Batch: 1` rather than their actual material quantity. | Offer `To inspect`, `Awaiting review`, `Failed / on hold`, and `All` using ordinary URL filters. Show correctly scoped counts across the filtered dataset, not page counts. Add source-reference search and display quantity with unit plus coverage. Reuse existing summary/filter patterns, aligning date and search scopes; the current completed-only analytics summary is not a drop-in pending-work counter. |
| P2 | **Record flow always includes `Cancelled`.** Completed PASS and FAIL records show a pending cancellation step. In-process records can show checker review pending even though their policy does not require it. | Build the flow from actual policy and state. Show cancellation only as the record's alternate final outcome. Mark reviewer step skipped or omit it when not required. For failures, distinguish `Inspection failed` from `Recovery resolved`; completed inspection does not mean stock has been released. |
| P2 | **Generic defect entry creates repeated typing.** Operators need to describe several failures and then classify whether they represent physical defects. An out-of-limit size already determines a physical defect, yet `No` remains selectable and only blocks submission later. | Offer a few suggested descriptions such as cracks, contamination, incorrect label, size out of limit, and missing document, with editable text and a custom option. Enter the unique defective-piece count once for the batch. When actual size proves a physical defect, explain that fact and do not offer a contradictory `No` choice. Keep human confirmation for ambiguous attribute failures. |
| P2 | **Links can imply unavailable cross-module access.** Entity-source links are permission-aware in the API, but product, specification and output-WO links are constructed directly by the page. Default QC permissions do not necessarily include full product/WO access. | Apply destination permission checks to every linked record. Keep record reference visible as plain text when access is unavailable. Do not solve a blocked link by granting broad cross-module edit access. Add a direct saved item-plan link using existing inventory permissions. |
| P3 | **Checklist pages request hidden SPC data.** The detail page requests capability options and SPC whenever a specification exists, even though it hides SPC for checklist capture. | Disable those queries for checklist inspections. Keep SPC available only where meaningful measured history and specification revision exist. Never calculate Cp/Cpk from nominal values or PASS/FAIL counts. |

## Safe automation

- Keep existing automatic source-to-inspection creation, automatic size evaluation, NCR creation and eligible WO closure. Improve their visible outcome instead of adding parallel workflows.
- After submission, show the committed result and the next responsible role: independent QC reviewer, QC disposition owner, Warehouse receipt acceptance, or Production recovery. State the downstream action as completed only when the real linked record confirms it; otherwise show pending or failed handoff.
- Reuse current review notifications and Action Center. Add bounded, deduplicated reminders for outstanding reviews or handoff failures if their current age and responsibility are available. Do not repeatedly notify every QC user on each page refresh.
- Prefill stable source identity, quantities, units, pinned requirements and suggested defect descriptions. Do not prefill actual readings, inspector verdicts, reviewed evidence or coverage attestations.
- Keep `PASS remaining checks` as a deliberate action with its existing performed-check confirmation. Do not make it an automatic default or include unanswered size readings.

## Keep these strengths

The current five-stage flow already enforces atomic results, immutable specification references, whole-piece validation, unique defect counts, stale-result rejection, independent high-risk review, failed-stock holds, and role restrictions. Size inputs are not filled from nominal values. Regular checks use PASS/FAIL. PASS/FAIL touch buttons have 44 px targets. Fresh desktop/mobile captures have no document-level horizontal overflow. Shared tokens and components preserve the system's visual identity.

For frontend follow-up, use Impeccable harden/clarify for states and quantities, layout/adapt for checklist priority and mobile order, distill for compact rows, and polish only after the process issues are resolved. The implementation should finish with focused regressions for source-linked recovery, mixed PASS/FAIL analytics, transient authentication errors, saved/unsaved checklist drafts and role-aware links, followed by one batched desktop/mobile visual check.

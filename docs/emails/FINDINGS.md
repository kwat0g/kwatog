# Email audit findings

Date: 2026-10-20. Static findings only; reachability and runtime impact remain unverified. Fixes belong in separate functional/security changes, not the email-template work.

| ID | Finding | Evidence / impact | Follow-up |
|---|---|---|---|
| EF-001 | Local development mail initially could reach external SMTP | `.env` and `api/.env` used SMTP with AWS Mail Manager credentials. Both now use `MAIL_MAILER=log`, credentials are blank, and Horizon was restarted. The shared-foundation branch adds redirect-or-block enforcement. | Keep local mail on log or a verified sink; verify the deployed guard before any non-production send. |
| EF-002 | Company settings need owner verification | Shared foundation now requires `company.legal_name` and `company.address` instead of using fallback literals, and makes the other optional identity values settings-only. The local settings rows exist; sales inbox and VAT status match the old fallback strings. | Owner verifies settings before external send. Accountant reviews statutory fields. |
| EF-003 | Welcome/reset messages include temporary passwords | Auth and HR notification constructors accept temporary password strings and their mail bodies include them. Exact active call paths need confirmation. | Trace reachability; replace with secure activation/reset flow. Security review. |
| EF-004 | Some email transport remained synchronous | Customer sales-order decision and supplier PO decision now enqueue after commit on the dedicated mail lane. Payslip still calls `Mail::send` inside its existing queued low-lane job; critical-alert notification is synchronous to preserve its alert-owned retry state. | Keep payslip in sensitive-delivery review; redesign alert delivery state before moving its transport. |
| EF-005 | Generic emails vary in sensitivity but share one body path | `NotificationService` can queue `UserNotificationMail` with arbitrary caller title/message/link for opted-in notification types. | Classify runtime type keys and remove sensitive body details or restrict eligibility as a separate privacy/RBAC change. |
| EF-006 | Delivery state lacks a common durable email ledger | Existing status tracking is per-feature; most send paths do not share queued/sent/failed logs or provider identifiers. | Add an email ledger with redaction and retention rules before building an Email Center. |
| EF-017 | Markdown email preheaders were dropped before reaching the HTML layout | Email views could provide `preheader`, but Laravel's shared `mail::message` component did not pass it into `mail::layout`; hidden preview text was absent from rendered messages. | Fixed in shared foundation PR #213 by forwarding the value; verified with shell and portal-email renders. |
| EF-018 | Shared email CSS blocked dark colors and forced 600px mobile overflow | Important light-mode styles overrode dark-mode media rules after CSS inlining, and the 600px table width exceeded a 390px viewport. | Fixed in shared foundation PR #213; browser previews verify responsive width and dark colors. Real email-client behavior remains unverified. |
| EF-020 | Dark-mode fallback links had low contrast | Browser preview showed rust-colored text links too dim against the dark email background. | Shared foundation PR #213 now uses a brighter dark-mode link color and preserves white button text. Browser screenshots rechecked. |
| EF-021 | Supplier PO cancellation mail used mutable values and render-time cancellation date | The queued event stored only a model reference, listener resolved the current vendor email, and the mailable read the PO/vendor during worker render. Cancellation date was `now()` at render time. | Fixed in PR #227 by snapshotting recipient and display values in the outbox event and passing a scalar snapshot to the mail. Existing pending outbox rows without snapshots will use current values when replayed. |
| EF-022 | Customer complaint email exposed internal severity, full description, and affected quantity, and used mutable record values | The external template included customer complaint detail fields and the queued listener/mailable rehydrated customer and complaint records at delivery time. | Fixed in PR #229 by snapshotting recipient/status/reference/product and limiting external content to those fields. Existing queued events without snapshots use current values on replay. Company privacy contact should review the data-minimization decision. |
| EF-007 | Finalized invoice mail could use a later customer address and changed invoice values | `InvoiceFinalized` queues its email listener. Laravel rehydrates its invoice model when that listener runs, so customer email, balance, customer name, and line items could differ from the values at issue time. | Fixed in the separate invoice snapshot change: capture issue-time recipient and display fields in the event; test delay-shaped mutations before listener handling. |
| EF-008 | Official receipt mail could use a later customer address and changed receipt/invoice values | `OfficialReceiptIssued` queues its email listener with a model only. Customer email, receipt number/date/amount, and invoice number could change before the listener reloads relations and queues mail. | Fix in this snapshot PR: capture recipient and display values in the event; test mutations between event creation and listener handling. |
| EF-009 | Official receipt email has no official receipt document link or attachment | `CustomerOfficialReceiptMail` points to the related invoice portal page; no customer receipt page or official-receipt PDF route/view was found in the SPA/API search. Email body cannot be assumed to be an acceptable statutory receipt. | Separate product/accounting decision: accountant confirms the required customer document and delivery channel; if required, add a source-backed receipt PDF/portal route in its own PR. |
| EF-010 | Queued invoice dunning can show later invoice/customer values | `ArDunningService` selects the customer address and queues `InvoiceDunningMail` with a serialized `Invoice`; Laravel can reload the model and its customer after the scan transaction commits. The customer can receive the address captured at scan time but see a newer balance, invoice number, date, or name. | Fix in separate dunning snapshot PR: capture recipient and display fields when the reminder tier is claimed; test mutation between queueing and rendering. |
| EF-011 | Dunning email wording assumed fixed 15/30-day thresholds | The old view chose escalation copy with `$tier >= 15` and `$tier >= 30`, while `accounting.ar_dunning.tier_days_csv` controls actual tiers. This exposed obsolete threshold claims and pressure language. | Fixed in E-003 template PR: reports actual overdue days without hardcoded tier labels. |
| EF-012 | Dunning volume scales one email per overdue invoice | The scheduled scan queues one customer email for every invoice crossing a tier, without per-customer aggregation or rate limit. Customers with many overdue invoices can receive a burst. | Product decision needed on grouping into statements/digests; preserve current per-invoice trigger until approved. |
| EF-013 | Credit note email has no external credit-note page or PDF | `PartyCreditNoteMail` links to the customer/supplier portal root, not the credit note; no external credit-note page or PDF view was found in API/SPA sources. The email is not a source-backed document attachment. | Still open: accountant confirms required customer/supplier document delivery; add source-backed PDF/portal access in a separate PR if required. |
| EF-014 | Queued credit note mail could use later party and credit-note values | `CreditNoteFinalized` dispatches an event with only a model, then the queued listener reloads party/document relations. A party address, amount, reason, or note number changed before listener execution could mismatch the finalization event. | Fix in separate snapshot PR: capture party address and display fields in the event; test changed records before listener handling. |
| EF-015 | Credit-note free-text reason was sent to an external party | The same unclassified `reason` field entered by accounting was interpolated into both customer and supplier mail; no separate public-safe reason field exists. | Fixed in E-004 template: omit the unclassified free text. Accountant reviews external wording. |
| EF-016 | Portal invitation emailed a reusable temporary password | Customer and supplier invitations queued the login password in plaintext in Redis/mail content. It had no expiry; security depended on recipient changing it after login. | Fixed in separate security PR: save an unknown random password and send a one-time setup link using the existing 60-minute portal reset token. E-005 visual redesign remains separate. |
| EF-019 | Supplier invoice confirmation rehydrates mutable records at delivery time | Queued mail held a Bill model and read supplier, invoice, amount, count, and portal-link values when the worker rendered it. Later edits could make the confirmation disagree with submission-time data. | Fixed in PR #225 by freezing displayed values when the mail is created; source records remain unchanged. |
| EF-023 | Sales order confirmation email rendered mutable record values after confirmation | The outbox event held a model reference; the listener and Mailable loaded current customer, line, total, and URL values, so queued mail could show a later edit. The template also formatted financial values through floats. | Snapshot semantics fixed in #231; E-010 redesign now uses the system CurrencyDisplayService. |
| EF-024 | Customer sales-order decision email used mutable records and exposed recipients | Decision email rendered current customer/order/response data at worker time. Active portal-user emails were sent in one visible `To` list; malformed addresses blocked fallback to the customer address, and no eligible address was silently ignored. | E-011 snapshot PR freezes message fields, validates/deduplicates active customer-scoped recipients, queues one message per address, and alerts sales when no valid recipient exists. |
| EF-025 | Candidate emails could display later interview/application values and internal interview outcomes | Application receipt/interview mail read mutable records at worker time. Interview outcome updates were considered candidate-visible and the update template exposed `Passed`/`Failed`. E-013 public status labels were shadowed by identically named public mailable properties, exposing raw enum values. | Snapshot and outcome fixes in PR #235; E-012–E-015 redesign in PR #236 renames view data to preserve public labels and strips unsafe Markdown. Personal-data handling needs HR/legal/data-protection review. |
| EF-026 | SPA authentication redirects dropped the requested query, fragment, and password-change return path | `AuthGuard` kept only `location.pathname`; a required password change sent users to the dashboard. Email deep links could return to the generic module or be lost. | Fixed in PR #237 by preserving the same-origin relative route through sign-in and required password change; test protects the complete return path. |
| EF-027 | Payslip email attached highly sensitive payroll PDF | `SendPayslipEmailJob` generated and attached the full payslip, including payroll fields, to employee email. The authenticated employee-only PDF route already exists. | Fixed in PR #238: email contains only period details and links to an authenticated confirmation page; PDF downloads only after an employee click. HR/legal/data-protection review required. |
| EF-028 | Supplier PO decision exposed active portal addresses in a shared To header | `SupplierResponseService::emailSupplierDecision()` passed every active portal user's email in one `Mail::to($recipients)` call, revealing co-recipient addresses. Invalid addresses also prevented fallback to the vendor address. | Fixed in draft PR #240: validate/deduplicate active addresses, queue one copy per recipient, use a valid vendor fallback, and send a permission-scoped in-app failure notice when no external address can receive the decision. |
| EF-029 | Supplier PO publication email could arrive before the PO became supplier-visible | `SupplierPortalDispatchGateway::publish()` queued the email while the PO was still `Approved`; `SupplierDispatchService` marked it `Sent` afterward. The supplier portal intentionally hides approved-but-unsent POs, so a fast worker or click could hit an unavailable record. | Fixed in draft PR #241 by wrapping publication, dispatch completion, and the sent transition in one transaction; the mailable's after-commit queue now releases after the PO is visible. |
| EF-030 | Supplier PO email-failure notices used permission without PO row visibility | `SupplierPortalDispatchGateway` selected every active user with `purchasing.view` for missing-address and queued-delivery alerts. That permission alone does not grant visibility to every PO; it also seeded fallback IDs on the queued mailable. | Fixed in draft PR #242: resolve active users with `purchasing.view` and `PurchaseOrderAccessPolicy::canView()` for this exact PO, then reuse that set for immediate and queued-failure alerts. |
| EF-031 | Supplier RFQ lifecycle email could use later RFQ, supplier, and recipient values | The durable RFQ event held only IDs and kind. Its queued listener reloaded the RFQ and invitation before queueing another mail job, so a changed deadline, title, contact, status, or vendor email could mismatch the triggering event or go to a different address. | Fixed in draft PR [#244](https://github.com/kwat0g/kwatog/pull/244): store event-time RFQ and per-invitation display/recipient values in the outbox event; queued mail uses only its supplier-specific snapshot. Existing old outbox payloads and queued mail retain fallback behavior. |
| EF-032 | Retried RFQ lifecycle listener could queue duplicate supplier notices | The queued listener can partially queue notices and then retry. It had no stable per-event/per-invitation delivery key, so duplicate listener attempts received unrelated email-log keys and could deliver the same notice twice. | Fixed in draft PR [#245](https://github.com/kwat0g/kwatog/pull/245): derive a stable delivery key from RFQ, lifecycle kind, event deadline, and invitation; verify retries reuse the key and rely on the shared delivery ledger's duplicate-send suppression. |
| EF-033 | Shared email footer asserted unverified certification and reply/copyright claims | The shared footer rendered a configured certification label, a hardcoded “All rights reserved” claim, and a hardcoded do-not-reply instruction; the integration test mail also exposed VAT and certification settings. These statements were not approved per email. | Fixed in shared email footer PR #246: remove certification, VAT, copyright, and reply-policy claims from email output; retain verified identity/contact settings and configured disclaimer. |

Findings were recorded during discovery; subsequent email PRs address the issues noted. EF-028 and EF-031–EF-033 are fixed in their respective draft PRs.

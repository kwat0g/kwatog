**Audit date:** 2026-08-16
**Scope:** discovery audit of the full worktree — module inventory, data
integrity, authorization, API and frontend layers, cross-cutting integrations,
and CI gate health.
**Method:** source inventory, live `route:list` and PostgreSQL catalogue
queries, and measured tool runs. File/line references are to the current
worktree.
**Relationship to the 2026-08-13 register:** additive. F-001–F-038 are
unaffected; this register begins at F-039.

**Retracted observation — suspected test-suite non-determinism.** The audit
initially reported the suite as order-dependent, having observed 5, 2, and 1
failures across three runs of `--filter='Import|Badge'`. This was an artifact of
the audit method: a killed `docker compose exec` left a `phpunit` process
running inside the `api` container while new runs started, so two suites wrote
to the shared `ogami_test` database concurrently. Three subsequent serial runs
produced identical results every time — 1 failed, 30 passed, 253 assertions,
the F-041 failure alone. No F-number is assigned; a retracted observation is not
a finding. Recorded so it is not re-investigated.

**Non-defect — `api/app/Modules/HR/Services/SeparationService.php:291-297`.** larastan
anchors the report at the `EmployeeLoan::query()` chain start on :291; the `->count()` it
objects to is on :297. It reports "Called 'count'
on Laravel collection, but could have been retrieved as a query." The code is
`->lockForUpdate()->get(['id'])->count()`. PostgreSQL rejects `FOR UPDATE`
combined with aggregate functions, so `->count()` cannot carry the row lock and
rewriting it would reintroduce the loan-settlement race the preceding comment
exists to prevent. Suppressed in `api/phpstan.neon` with that reason inline.

### F-039 — larastan is installed but never activated, leaving the static analysis gate decorative and failing on a false positive

- **Module / feature:** CI quality gates / static analysis.
- **Related modules:** every module under `api/app`.
- **Category:** Engineering productivity / defect detection.
- **Affected roles:** all contributors; no runtime user impact.
- **Current Behavior:** `api/composer.json` requires `larastan/larastan ^3.10` and `.github/workflows/api-tests.yml:86` runs `vendor/bin/phpstan analyse app --memory-limit=1G`, but no `phpstan.neon` exists anywhere in the repository. PHPStan therefore runs at its default level 0 without larastan's extension and has no knowledge of Eloquent, facades, or container bindings.
- **Problem:** The gate reports exactly one error — `Call to static method table() on an unknown class DB` at `api/app/Console/Commands/CheckRecruitmentBottlenecks.php:188` — which is a false positive, since Laravel registers the `DB` alias via `Facade::defaultAliases()` even with no `aliases` key in `config/app.php`. The gate exits 1, failing `api-tests` on every push, while real defects go unreported.
- **Real-world scenario:** A contributor pushes correct code, sees `api-tests` fail on an error that is not a defect, and learns to ignore the gate. Genuine issues such as F-040 ship unnoticed.
- **Root Cause:** A dev dependency was added without the configuration that activates it.
- **Recommended Improvement:** Add `api/phpstan.neon` including `vendor/larastan/larastan/extension.neon` at `level: 0`, with documented `ignoreErrors` for the `SeparationService` locked-count non-defect. Defer level ≥1 to a dedicated tranche.
- **Ideal Process:** Static analysis understands the framework it analyses, so every reported error is actionable and the gate is trusted.
- **New Feature/Module Required:** No. Configuration only.
- **Cross-Module Impact:** Analysis coverage across all of `api/app`.
- **Evidence:** `api/composer.json` (`larastan/larastan ^3.10` under `require-dev`); `.github/workflows/api-tests.yml:86`; absence of any `phpstan.neon`; measured error counts on `app/` (1,376 files) — without larastan: 1 / 3,327 / 8,410 / 9,681 at levels 0 / 1 / 3 / 5; with larastan: 2 / 2,107 / 3,892 / 5,151. That sweep was measured **before** this tranche's fixes; Task 2 removed one of the two level-0 items, so today's tree reports **1** at level 0 with larastan active (the `SeparationService` locked-count item alone), which the single documented suppression takes to 0. `php artisan recruitment:check-bottlenecks` exits 0, proving the reported error is not a runtime fault.
- **Priority:** P1.
- **Impact:** CI blocked; real defects undetected.
- **Complexity:** S.

### F-040 — EmailBrandingService reads env() after config:cache, so its environment fallback tier is dead in production

- **Module / feature:** Common / transactional email branding.
- **Related modules:** HR recruitment mail (`ApplicationReceivedMail`, `ApplicationStatusUpdatedMail`, `InterviewScheduledMail`, `InterviewDetailsUpdatedMail`), `EmailIntegrationTestMail`.
- **Category:** Configuration correctness / dev-prod divergence.
- **Affected roles:** every recipient of transactional email.
- **Current Behavior:** `api/app/Common/Services/EmailBrandingService.php:78-82` resolves each branding key through three tiers — settings row, then `env(STRTOUPPER_KEY)`, then a hardcoded default.
- **Problem:** `docker/php/prod-entrypoint.sh:15` and `Makefile:219` run `php artisan config:cache`. After that, `env()` returns null for anything not read through `config()`, so tier 2 never fires in production while still firing in development. The tier is independently broken for `email.brand_name`, which derives `EMAIL_BRAND_NAME` while `api/.env.example` defines `COMPANY_EMAIL_BRAND_NAME` — that lookup has never matched anything.
- **Real-world scenario:** An operator sets `COMPANY_CERTIFICATION` in the production `.env`, verifies the branding locally where the env tier still works, deploys, and the certification line silently reverts to the hardcoded default in customer-facing mail.
- **Root Cause:** A configuration tier that only functions when the configuration cache is cold, in a deployment that always warms it. The repository already documents this exact trap at `api/routes/api.php:57-58`.
- **Recommended Improvement:** Delete the `env()` tier. Settings is the source of truth and is seeded from env at migrate/seed time, which is where environment values legitimately enter.
- **Ideal Process:** One configuration source per value, behaving identically in development and production.
- **New Feature/Module Required:** No.
- **Cross-Module Impact:** All branded transactional mail.
- **Evidence:** `api/app/Common/Services/EmailBrandingService.php:71-86`; `docker/php/prod-entrypoint.sh:15`; `Makefile:219`; `api/routes/api.php:57-58`; seeding coverage in `api/database/migrations/0123_seed_company_branding_settings.php:17-26`, `0358_seed_landing_contact_setting.php`, and `api/database/seeders/SettingsSeeder.php`.
- **Priority:** P2.
- **Impact:** Silent, environment-only branding regression with a working fallback.
- **Complexity:** S.

### F-042 — PHPUnit's non-forced APP_ENV=testing loses to docker-compose's APP_ENV=local, so the suite never runs in the environment it declares

- **Module / feature:** Test harness / environment isolation.
- **Related modules:** `App\Common\Traits\HasHashId` (applied to every model) and `App\Common\Middleware\LogSlowQueries`; the suite it misconfigures is 1,772 test methods across 356 files.
- **Category:** Test integrity / configuration correctness.
- **Affected roles:** all contributors; no direct runtime user impact.
- **Current Behavior:** `docker-compose.yml:11` injects `APP_ENV=${APP_ENV:-local}` into the api container's real process environment. `api/phpunit.xml:35` declares `<env name="APP_ENV" value="testing"/>` with no `force="true"`, and PHPUnit skips a non-forced `<env>` whose name is already present in the process environment. The declaration therefore loses: `app()->environment()` returns `local` for the whole local suite.
- **Problem:** Any code branching on the testing environment takes the wrong branch locally. `api/app/Common/Traits/HasHashId.php:33` and `:58` accept a raw integer route ID when `app()->environment('testing')`; that binding path is exercised in CI — `.github/workflows/api-tests.yml:90` sets `APP_ENV: testing` as a real process variable — but never locally, where a numeric segment instead falls through to `app('hashids')->decode()` and `abort(404)` on :39/:64. `api/app/Common/Middleware/LogSlowQueries.php:52` defaults slow-query logging to **on** locally for the same reason, when the intent stated on :49 is "off in testing". Local and CI runs therefore execute different branches of the same tree.
  **Scope correction.** An earlier revision of this entry claimed that every `<env>` value in `phpunit.xml` also present in `api/.env` is silently inert and that tests read development configuration. That is false and was withdrawn. PHPUnit applies each non-forced `<env>` *before* Laravel boots, and Laravel's Dotenv is **immutable** — it will not overwrite a variable that is already set. Precedence is **process env > `phpunit.xml` > `api/.env`**. `DB_DATABASE=ogami_test`, the seven `COMPANY_*` keys, `TAX_PH_VAT_RATE`, `CACHE_STORE` and the rest all take effect and all override `api/.env`. `APP_ENV` is the sole inert declaration: 23 of the 24 apply.
- **Real-world scenario:** A contributor adds a route-bound endpoint test that passes a raw integer ID. It is green in CI and 404s on their machine, with nothing in the diff to explain it. Equally dangerous in the other direction: a guard written as `if (app()->environment('testing')) { return; }` to suppress an outbound call is assumed inert during the suite, and locally the call fires.
- **Root Cause:** A non-forced `<env>` cannot outrank a variable the Compose service already exports. `docker-compose.yml` supplies `APP_ENV` for runtime reasons and nothing exempts the test process from it.
- **Recommended Improvement:** Add `force="true"` to the `APP_ENV` entry **and to that entry only.** Do not generalise the attribute across the block: `api/phpunit.xml:64,66,68` declare `DB_HOST=db`, `DB_DATABASE=ogami_test` and `DB_PASSWORD=ogami_dev_pw`, while `.github/workflows/api-tests.yml:93,97` supply `DB_HOST=127.0.0.1` and `DB_PASSWORD=ogami_ci_pw` as process variables for the runner's own service containers. Forcing those entries would override CI's coordinates and point the entire runner suite at the Compose hostname `db`, which does not resolve on a GitHub runner. Those declarations are non-forced *on purpose* — CI must be able to outrank them.
  Note also that the attribute alone does **not** achieve the Ideal Process below. Laravel switches env files only when `.env.{APP_ENV}` exists, and `api/.env.testing` is gitignored (`.gitignore:12`) and untracked — present in some working copies, absent in CI and in a fresh clone. Forcing `APP_ENV=testing` therefore makes *which env file loads* machine-dependent, trading one divergence for a less visible one; on a machine that has the file, the eight keys listed under Evidence lose their `api/.env` values because that file does not carry them. ~~Genuine env-file isolation needs a committed testing env file carrying the `COMPANY_*` and `ADMIN_*` keys, which is a larger change than this finding.~~ **That prescription is RETRACTED (2026-08-19) — it named the wrong remedy, and a weaker one.** A `<php><env>` entry in `phpunit.xml` is applied before Laravel's `LoadEnvironmentVariables` bootstrapper, and Laravel's Dotenv is **immutable**, so a declared key outranks *every* loaded env file — `api/.env`, `api/.env.testing`, or any future committed one. Declaring the keys in the tracked `<env>` block is therefore strictly *stronger* than committing a `.env.testing`, which would itself lose to the same block and would still be overridable by an operator's local `.env.testing` on the machines that have one. It also needs no new tracked file. `api/phpunit.xml:52-57` already states this precedence; this entry did not, which is how the two ended up disagreeing. The remedy actually applied is the one this paragraph's *first* half asks for and the Evidence section's closing sentence names: declare the keys. See the 2026-08-18 and 2026-08-19 Status notes.
- **Ideal Process:** The test suite's declared environment is the environment it runs in, identically on a developer machine and in CI.
- **New Feature/Module Required:** No.
- **Cross-Module Impact:** Every model, via `HasHashId` route binding; any future `environment('testing')` guard.
- **Evidence:** `api/phpunit.xml:35`; `docker-compose.yml:11`; `.github/workflows/api-tests.yml:90,93,97`; `api/app/Common/Traits/HasHashId.php:33,58`; `api/app/Common/Middleware/LogSlowQueries.php:49-52`. Measured by replaying `phpunit.xml`'s non-forced `<env>` semantics and then booting the framework through `Illuminate\Contracts\Console\Kernel::bootstrap()`: `APP_ENV` is the only skipped declaration (23 applied), `app()->environment()` → `local`, `config('database.connections.pgsql.database')` → `ogami_test` (not `api/.env`'s `ogami`), `config('cache.default')` → `array`, `env('TAX_PH_VAT_RATE')` → `0.12`. Pre-setting `DB_DATABASE=phpunit_sentinel` and `COMPANY_LEGAL_NAME=phpunit_sentinel_co` the way PHPUnit does returns both sentinels after a full boot, confirming `phpunit.xml` outranks `api/.env`.
  Separately — and this is a **distinct** observation, not evidence of the missing `force="true"` — the keys `phpunit.xml` never declares do fall through to `api/.env`: `COMPANY_CERTIFICATION`, `COMPANY_SALES_INBOX_EMAIL`, `COMPANY_EMAIL_BRAND_NAME`, `COMPANY_LOGO_PATH`, `ADMIN_NAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ACCOUNTING_FUNCTIONAL_CURRENCY_CODE`. `api/.env` currently supplies four of them (`:14,17,23,91`) and leaves the other four unset, so those resolve to their in-code defaults. `api/.env:17` pins `COMPANY_CERTIFICATION` to a string byte-identical to its hardcoded fallback, which is what made F-040's env tier indistinguishable from its default tier — but `COMPANY_CERTIFICATION` appears **0** times in `api/phpunit.xml`, so `api/.env` legitimately supplies it and no `force` attribute would change that. ### F-044 — Budget consumption is classified from a rounded percentage, so a department at 99.95% is labelled exhausted and its purchase requests and purchase orders cannot be approved

- **Module / feature:** Accounting / Budgeting — budget availability and consumption classification.
- **Related modules:** Purchasing (PR and PO approval), Accounting (bill creation), the `GET /api/v1/budgets/check-availability` endpoint.
- **Category:** Money correctness / authorization gating.
- **Affected roles:** department heads and purchasing officers, who cannot approve; finance officers, who are asked to acknowledge an overrun that has not happened.
- **Current Behavior:** `App\Modules\Accounting\Services\BudgetEnforcementService::checkAvailability` (`api/app/Modules/Accounting/Services/BudgetEnforcementService.php:26`) computed `round((amount + spent + committed) / allocated * 100, 1)` and compared that percentage against the persisted `budget.warning_ratio` / `critical_ratio` / `exhausted_ratio` / `overdrawn_ratio` settings. `BudgetService::checkConsumption` (`api/app/Modules/Accounting/Services/BudgetService.php:89`) made the same comparison through `Budget::getUtilizationPercentAttribute` (`api/app/Modules/Accounting/Models/Budget.php:98`), which is rounded to one decimal for the same reason.
- **Problem:** `budget.exhausted_ratio` is exactly `1` in the live settings table, so rounding to one decimal makes every consumption level from **99.95%** upward read as `100.0` and classify `exhausted`. Worked example: **1,000,000.00** allocated, **999,000.00** already consumed, **500.00** requested → **99.95%** → `round(…, 1)` → **`100.0`** → **`exhausted`** — for a department that genuinely has 1,000.00 available and is asking for 500.00 of it.
  That label is not advisory. `assess()` (`:97`) stamps `budget_warning_level` onto the document at `:102-107` with **no** enforcement-mode guard; the mode is consulted only at `:109`, and only to decide whether to throw on the spot. `assertAcknowledged()` (`:143`) then throws whenever `budget_warning_level` is `exhausted` or `overdrawn` and no acknowledgment is recorded, and it has no mode guard either. It is called from `PurchaseOrderService::approve` (`api/app/Modules/Purchasing/Services/PurchaseOrderService.php:347`) and `PurchaseRequestService::approve` (`api/app/Modules/Purchasing/Services/PurchaseRequestService.php:357`). So the false `exhausted` label blocked PO and PR approval in **every** enforcement mode, including the live `warn`: the block lands at the `assertAcknowledged` gate rather than inside `assess()`, which is precisely why turning the mode down to `warn` — or to `off` — did not relieve it.
  **Scope limit on the second call site, stated deliberately.** `BudgetService::checkConsumption` carries the identical rounding defect but has **no production caller**: in the whole tree it appears only as its own declaration and in this tranche's test. It never drove a live alert, badge or label, and this entry makes no such claim — an earlier draft of the Tranche B plan asserted it was "driving alert and label state", which the call graph does not support. That half is registered as prospective and drift-preventing: the two classifiers are unified so they cannot disagree the moment the second one is wired to a caller.
- **Real-world scenario:** A department finishes the fiscal year having committed 99.96% of its operating budget. It raises a 500.00 PR for consumables it can plainly afford. The PR is stamped `exhausted`, and `assertAcknowledged` refuses the approval until a finance officer with `budgeting.approve` acknowledges an overrun that does not exist. Operators learn that the budget module lies near the ceiling and start routing spend around it, or finance acknowledges reflexively — which is worse, because the acknowledgment is the control that exists for real overruns.
- **Root Cause:** A display value used as a decision input. `round(consumed / allocated * 100, 1)` discards 0.05% of resolution, and the ratio it is compared against sits exactly on the boundary where that resolution decides the outcome.
- **Recommended Improvement:** Classify by comparing money to money and never divide: `consumed >= allocated × ratio`, evaluated with bcmath through `App\Common\Support\Money`. Extract that comparison into one classifier both call sites share, so they cannot drift apart again. Keep the percentage for display only, and guard its denominator explicitly — the pre-existing `available <= 0` check is **not** a sufficient guard, because `available = allocated − spent − committed`, so a negative `spent` or `committed` yields `available > 0` with `allocated == 0`, and dividing there is a `DivisionByZeroError` on PHP 8.
- **Ideal Process:** Money decisions compare exact decimal amounts. Percentages are presentation, and nothing that gates a document reads one.
- **New Feature/Module Required:** No. One shared support class (`App\Modules\Accounting\Support\BudgetConsumptionLevel`) plus signature changes to services that already exist.
- **Cross-Module Impact:** PR and PO approval (no longer blocked in the 99.95%–99.99% band), bill creation via `BillService:145`, and the budget check-availability endpoint (`BudgetController:274`).
- **Evidence:** `api/app/Modules/Accounting/Services/BudgetEnforcementService.php:26,66,97,102-109,143`; `api/app/Modules/Accounting/Services/BudgetService.php:89`; `api/app/Modules/Accounting/Models/Budget.php:98,104`; `api/app/Modules/Purchasing/Services/PurchaseOrderService.php:347`; `api/app/Modules/Purchasing/Services/PurchaseRequestService.php:357`. Live settings queried on the running database: `budget.warning_ratio` `0.8`, `budget.critical_ratio` `0.95`, `budget.exhausted_ratio` `1`, `budget.overdrawn_ratio` `1.2`, and `budgeting.enforcement_mode` `"warn"` — so the enforcement mode is live at `warn` and the block still occurred, because it occurs at the `assertAcknowledged` gate and not in `assess()`. `checkConsumption` has no production caller, confirmed by grepping the whole `api/` tree for the symbol: the declaration and this tranche's test only. Regression proof: `BudgetConsumptionLevelTest` — **7 tests / 12 assertions** (unit, the classifier in isolation); `BudgetEnforcementBoundaryTest` — **7 tests / 10 assertions** (through the real service and PostgreSQL, including the parity case asserting `checkConsumption` and `checkAvailability` classify identical figures identically). Both files were observed failing before their fixes landed. Full suite after the tranche: **1837 passed**, exit 0. PHPStan with larastan active: `[OK] No errors`.
- **Priority:** P1.
- **Impact:** Purchase requests and purchase orders could not be approved for any department in the 99.95%–99.99% consumption band, in every enforcement mode, and the finance acknowledgment control was devalued by being demanded when nothing was overdrawn.
- **Complexity:** M.

### F-045 — Money crosses the budget and approval gates as float, so the VP approval step on purchase requests and purchase orders is routed on binary approximations

- **Module / feature:** Common / approval workflow and Accounting / budget enforcement — the money parameters of the gate signatures.
- **Related modules:** Purchasing (PR submit and urgent-skip, PO submit and approve), Loans, HR (salary adjustment), Accounting (bill creation, budget API and resource).

- **Affected roles:** every approver on the purchase-request and purchase-order chains, and specifically the VP step, whose participation is what the comparison decides.
- **Current Behavior:** `Budget::getAvailableAttribute` (`api/app/Modules/Accounting/Models/Budget.php:81`) returned `(float) ($total_allocated - $total_spent - $total_committed)` and fed `BudgetEnforcementService`'s block/allow comparisons directly; `checkAvailability` (`:26`), `assess` (`:97`) and `enforce` (`:162`) all declared `float $amount`. `ApprovalService::submit` (`api/app/Common/Services/ApprovalService.php:33`) declared `?float $amount` and decided step skipping with `(float) $step['threshold']` and `$amount < $threshold` (`:50`); `HasApprovalWorkflow::submitForApproval` (`api/app/Common/Traits/HasApprovalWorkflow.php:21`) mirrored that signature. `PurchaseRequestService::submitUrgent` (`:288`) compared `$total <= $limit` as floats (`:295`). Every caller cast an exact decimal column to float on the way in.
- **Problem:** This is **live**, not latent. An earlier revision of this entry — and the Tranche B plan and spec — called it latent on the strength of a database query that used `LIMIT 3` and happened to sample three workflows carrying no threshold. Corrected against the whole table: `api/database/seeders/WorkflowSeeder.php:65,75` sets `'threshold' => 50000.00` on the **final VP step** of both `purchase_request` and `purchase_order`, and the live database has exactly **2 of 17** `workflow_definitions` rows whose `steps` JSON carries a `threshold` — those two, each `"threshold":50000` on the VP step. The float comparison in `ApprovalService::submit` was therefore deciding whether **VP approval is skipped** on the two highest-value approval workflows in the system: an authorization-routing decision on money, taken on binary approximations of decimal figures.
  **What this entry does not claim.** No misroute is demonstrated at today's data. `50000` is exactly representable in binary, as are the peso amounts either side of it, so the comparison happens to land correctly at that threshold. The defect is that the correctness of a money authorization control rested on that accident rather than on the comparison: move the threshold to `50000.10` — a JSON number carrying centavos, which `json_decode` hands to the service as a genuine float — and the routing decision is made on approximations. Note also that the `workflow_definitions.amount_threshold` **column** is not the mechanism, despite the name and the docblock that referenced it: it is populated with `50000.00` on exactly those two rows, but nothing reads it at decision time — only `$step['threshold']` inside the `steps` JSON is consulted.
  **One mechanism in this cluster is genuinely inert, and is recorded as such.** `purchasing.urgent_skip_limit` is `0` in the live settings table and `submitUrgent` requires `$limit > 0` before it will skip a step, so its comparison decides nothing today. It is fixed alongside the rest so that raising the cap does not simultaneously introduce a float boundary.
- **Real-world scenario:** Finance raises the VP threshold to a figure with centavos — the kind of number a policy review produces — and a purchase order lands one centavo from it. Whether the VP is asked to approve a high-value PO is then settled by which side of a binary approximation the value falls on, with no record that a step was skipped for a reason other than the stated policy. The skip is written as `action = 'skipped'`, so from the audit trail it is indistinguishable from a correctly skipped step.
- **Root Cause:** Exact decimal columns cast to `float` at every gate signature in the chain, so precision was discarded before any comparison the gate could make. Compounded by the step threshold living in a JSON column as a JSON number: `json_decode` yields an int for an integral value such as today's `50000`, but a float as soon as the threshold carries centavos, and that conversion happens upstream of the service entirely.
- **Recommended Improvement:** Carry money as decimal strings through the gate signatures — `?string $amount` on `ApprovalService::submit` and `HasApprovalWorkflow::submitForApproval`, `string $amount` on `checkAvailability` / `assess` / `enforce` — and compare with bcmath via `App\Common\Support\Money`. Return the exact remaining balance from `Budget::getAvailableAttribute` as a string, casting to float only at the API boundary in `BudgetResource`, as that resource already does for `total_allocated` / `total_spent` / `total_committed`. Store a step threshold as a JSON **string** (`"50000.00"`), since a JSON number carrying centavos is decoded to a PHP float before the service is reached. Pin the wire format of the check-availability `amount` parameter to a canonical decimal: bcmath's grammar is narrower than Laravel's `numeric`, so `1e3` and a padded ` 1` satisfy validation but make `bccomp` raise `ValueError`, which the removed `(float)` cast used to absorb — without a regex rule a validated request becomes an HTTP 500 instead of a 422 naming the field.
- **Ideal Process:** Money is exact from the database column to the comparison that decides an authorization outcome, and is converted to float only for display.
- **New Feature/Module Required:** No. `App\Common\Support\Money` already exists and is used elsewhere in the codebase.
- **Cross-Module Impact:** All amount-bearing approval submissions — `PurchaseRequestService:234,290`, `PurchaseOrderService:329`, `LoanService:200`, `SalaryAdjustmentService:55` — plus every budget gate caller and the budget API boundary.
- **Evidence:** `api/app/Modules/Accounting/Models/Budget.php:81`; `api/app/Common/Services/ApprovalService.php:33,50`; `api/app/Common/Traits/HasApprovalWorkflow.php:21`; `api/app/Modules/Purchasing/Services/PurchaseRequestService.php:288,290,294-295`; `api/database/seeders/WorkflowSeeder.php:65,75`. Live database, full table rather than a sample: 17 `workflow_definitions` rows, of which exactly `purchase_request` and `purchase_order` carry `"threshold":50000` on their final VP step, and `purchasing.urgent_skip_limit` is `0`. Regression proof: `ApprovalThresholdBoundaryTest` — **4 tests / 4 assertions**, covering one centavo below the threshold (skipped), exactly the threshold (retained, since the semantic is strict `<`), one centavo above (retained), and a step with no threshold (always retained); it seeds its own workflow because `RefreshDatabase` leaves `workflow_definitions` empty and the boundary needs a threshold of its own rather than the shipped rows' single value. `BudgetCheckAvailabilityAmountTest` — **4 tests / 10 assertions** on the API boundary, asserting `1e3` and `+1000` are 422s naming `amount` rather than reaching bcmath. `ApprovalServiceTest` — **14 passed / 36 assertions** (pre-existing, updated for the new signature). - **Priority:** P1.
- **Impact:** A live authorization-routing decision on the two highest-value approval workflows was taken on floats. No misroute is demonstrated at the single seeded threshold, because `50000` is binary-exact — which is the finding: a money authorization control was correct by arithmetic accident rather than by construction.
- **Complexity:** M.

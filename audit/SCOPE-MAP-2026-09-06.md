## Shared / ambiguous territory (flag, don't fix, in unit audits)

Cross-module issues get resolved at Phase 2 consolidation.

1. **Entity ownership drift**
   - `Customer`, `Vendor` live in **Accounting** (`App\Modules\Accounting\Models`) but are
     CRM/Purchasing/B2B core entities.
   - `Product` lives in **CRM** but is MRP (BOM), Production, Quality, SupplyChain core.
   - `Machine`, `Mold` live in **MRP** but are Production/Maintenance core
     (`MaintenanceWorkOrder` is polymorphic `maintainable_type/_id`).
   - `Item` (Inventory) is MRP/Purchasing/Production/Maintenance/Assets core.
2. **GL posting fan-in** — Payroll, Bills (AP), Invoices/Collections (AR), asset
   depreciation, budget consumption all create `journal_entries` via Accounting's
   `PostingAccountResolver`/`SourceReferenceRegistry`/`JournalEntryService`. Any posting
   defect that crosses the boundary → flag cross-module.
3. **Approval machinery** — `HasApprovalWorkflow` trait + `approval_records` +
   `Common/Services/ApprovalService` serve Leave, Loans, PR/PO, Payroll, NCR,
   asset disposal, bill payment, salary adjustment. Unit audits own their workflow USAGE;
   the machinery itself belongs to unit 9.
4. **Aggregator row scopes** — Approval Queue / Global Search / Action Center must reuse
   each module's own row scope (`PurchaseOrderAccessPolicy`, `LoanAccessPolicy`,
   `DepartmentScope`). Unit 9 audits the aggregators; module units flag when their own
   scope is missing/leaky.
5. **Quality touchpoints** — incoming QC hooks GRN (Inventory), in-process hooks WO output
   (Production), outgoing hooks Delivery (SupplyChain), NCR hooks CRM complaints +
   replacement WOs (Production). Quality unit owns the touchpoint logic; host modules own
   their side.
6. **GRN** lives in Inventory but is the Purchasing→Quality→Accounting bridge (3-way match
   lives in Accounting/Purchasing).
7. **B2B portals** reuse Purchasing (PO/GRN/item listings), SupplyChain (shipments),
   Accounting (bills), CRM (SO/invoice/delivery/complaints) data. Portal unit audits portal
   code + portal guards; module-side defects get flagged cross-module.
8. **CreditNote** lives in Accounting but is the Return Management remedy path.
9. **Event backbone** — `OutboxService`, `ChainBroadcaster`, `ChainListener*`,
   `activity_events` (Common) feed the Chain monitor + ActivityStream on SO/PO/WO/NCR.
   Belongs to unit 9's adjacency; producers audited in their units.
10. **Notifications/Alerts** — `NotificationService`, `AlertEngineService`,
    `NotificationCatalog` (Common) are shared; per-module triggers audited in each unit.
11. **Cron** — `api/routes/console.php` (43 commands). Each unit checks its own scheduled
    commands; the ledger/scheduler infra is unit 9 adjacency.
12. **Document numbering** — `DocumentSequenceService` (Common) + `document_sequences`.
13. **Out of tier scope (shared infra, audited only as dependencies):**
    `Auth`, `Admin`, `Landing` modules; `api/app/Common/**` outside the files assigned to
    unit 9; `spa/src/components/{ui,layout,chain,brand}`; `api/app/Providers`;
    `api/app/Http` middleware. Findings there are logged cross-module, fixed only if on
    the critical path of an in-scope fix.

## Rules handed to every subagent

- Read-only audit (Phase 1): no code changes, no migrations, no branches.
- Finding taxonomy: Gap / Missing / Risk / Broken process / Stuck process / Bad practice
  + free-form "other". Cross-module findings flagged, not fixed.
- Every finding: `file:line`, severity (Critical/High/Medium/Low), one-line
  reproduction/evidence, effort (S/M/L).
- Project law (CLAUDE.md): Sanctum cookies only; HashIDs everywhere (never raw IDs);
  enums for status/type; money decimal-as-string across the API; `DB::transaction()` for
  financial ops; FormRequest `authorize()`; resources mask sensitive fields; migration
  naming by dependency not max+1.
- Test runs allowed only with `--filter` for the unit's own suite, one at a time,
  on `ogami_test` (sequential, never concurrent) — prefer static analysis.

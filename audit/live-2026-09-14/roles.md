## Identity Rules

The demo accounts below are from `docs/SEEDS.md` and `api/database/seeders/DemoAccountSeeder.php`. The common demo password is the seed literal `password`; it is not an environment secret. Never print environment variables, deployment passwords, session values, cookies, or reset tokens.

`buyer2` is a separate account with the same `purchasing_officer` role as `purchasing`. It is a distinct actor for creator/row-scope and self-approval tests, not a new role or proposed privilege change.

`portal@supp.test` and `portal@cust.test` are created by `GoldenPathDemoSeeder`, not `DemoAccountSeeder`. Their display names are derived from the first active vendor and first customer at seed time. Verify the linked tenant before execution; do not invent a supplier/customer identity. If `GoldenPathDemoSeeder` has not run, mark portal scenarios blocked by missing fixture rather than using an internal account.

## Distinct Approval Actors And Fixture Sufficiency

The overnight run must use the following actor map. “Insufficient” means the existing seeded account cannot perform the required role or a required distinct actor is absent; it does not authorize a privilege change.

| Workflow / control | Distinct actors required | Existing fixture assessment |
|---|---|---|
| Leave | Employee maker, `depthead`, `hr` | Sufficient for PROD employee path; use a separate employee fixture for maker/checker. |
| Overtime | Employee maker, `depthead` | Sufficient for PROD employee path. |
| Cash advance | Employee, `depthead`, `finance`, `vp` | Sufficient if the employee maker is not one of the approvers. |
| Company loan | Employee, `depthead`, `production`, `finance`, `vp` | Sufficient; `production` is the current seeded Manager step. |
| Purchase request | `depthead` or `purchasing` maker, `finance`, `vp` for threshold | Sufficient. The current chain is Finance → VP, not a buyer approval step. |
| Purchase order | `purchasing` or `buyer2` maker, `finance`, `vp` for threshold | Sufficient. `buyer2` is useful to prove a second same-role creator but is not the current money checker. |
| Salary adjustment | HR maker, `production`, `vp` | Sufficient for the current seeded role map; `hr` must not self-act. |
| Return request | `crm`/Sales maker, `depthead`, `production` | Sufficient for customer-return approval; warehouse/QC still needed for receive/inspect/dispose. |
| Asset disposal | Maker, `finance`, `vp` | Sufficient under current `WorkflowSeeder`. `SEEDS.md`’s older system-admin step must not be used as the live expectation. |
| Payroll | HR maker/computer, Finance checker/finalizer | Potentially insufficient as seeded if the active workflow literally requires HR to approve: `hr` lacks `payroll.periods.approve`. Execute the check and record the current behavior; do not grant a permission during the audit. |
| Budget | Budget maker, `vp` approver | Verify the actual maker permission and separate actor; do not use VP as maker. |
| Stock adjustment | `warehouse` maker, `finance` high-value checker | Sufficient for the seeded roles; preserve a high-value fixture. |
| PPAP | QC maker/reviewer/approver route | No distinct QC manager identity is seeded. The route currently uses one `quality.ppap.manage` gate; mark any same-user approval as a process question, not a permission change. |
| Separation clearance | `depthead`, `warehouse`, `maintenance`, `finance`, `hr` item owners | Sufficient for the current `WorkflowSeeder` role names. It is a direct clearance-item lifecycle, not a wired approval workflow. |
| Reserved definitions | Department transfer, maintenance request, 8D, bill payment, work order, NCR, separation clearance | Do not fabricate missing `manager`, `qc_head`, `qc_manager`, `maintenance_head`, or `warehouse_head` accounts. Current `WorkflowSeeder` uses seeded substitutes for some definitions, but reserved status remains non-live. |

## Role Test Order

1. Establish `employee`, `depthead`, `hr`, `finance`, `production`, `vp`, `purchasing`, `buyer2`, `warehouse`, `qc`, `maintenance`, `impex`, `crm`, and `driver` sessions independently; never reuse a browser session while claiming actor separation.
2. Run allowed-path checks first on disposable records, then repeat the same target with the nearest forbidden role via direct API.
3. Run self-approval and cross-department/tenant checks before advancing a record to its next state.
4. Use `admin` only for admin/recovery controls and for validating that business SoD expectations are not accidentally being treated as a wildcard pass.
5. Use portal identities only through their portal login and guard; do not infer portal authorization from internal role results.

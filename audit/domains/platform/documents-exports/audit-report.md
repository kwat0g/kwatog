# M011 — Documents & Exports audit report

Audit date: 2026-08-24  
Claim: platform / documents-exports  
Registry tier: 4  
Status: 📋 Plan Ready  
Session recommendation: separate-recommended

## Verdict

Production-readiness score: **50/100 — not ready for an unqualified release**.

The module has good primitives: generated files are intended to live on a private disk, document routes use hash binding and per-document permission mapping, the vault records checksums and audit rows, scheduled exports have a database lease, and spreadsheet values are written as explicit strings to reduce formula injection risk. The release risk is at the boundaries around those primitives. Export requests can bypass the declared column registry, the scheduled-export path does not reuse the export capability boundary, only the employee exporter is actually registered, the scheduled-export UI cannot create a schedule, and several official PDF services bypass the central vault entirely.

These are cross-layer security, capability, and contract issues. The majority of the work is medium/large and needs explicit decisions about export modules, document ownership, retention, and resource limits. No production-code fix was applied in this audit session.

## Findings

### M011-F01 — Broken/high: export requests bypass the declared column allowlist and can expose sensitive HR fields

Priority: **P0**  
Scope: **medium**  
Recommendation: **separate-recommended**

ExportController::resolveColumnsFromRequest() accepts arbitrary comma-separated or array values from the query string without intersecting them with ExportColumnRegistry::for($module) (api/app/Common/Controllers/ExportController.php:72-119). BaseModuleExport::map() falls back to direct model property access when a key is not registered (api/app/Common/Exports/BaseModuleExport.php:48-59). The employee exporter loads complete Employee models (api/app/Modules/HR/Exports/EmployeeMasterExport.php:28-43), and those models contain encrypted SSS, PhilHealth, Pag-IBIG, TIN, and bank-account attributes (api/app/Modules/HR/Models/Employee.php:31-58).

The intended registry exposes no government IDs or bank account number (api/app/Modules/HR/Exports/EmployeeMasterExport.php:49-120), and hr.employees.export is distinct from hr.employees.view_sensitive in the permission catalog (api/database/seeders/RolePermissionSeeder.php:57-65). A caller who has the ordinary export permission can nevertheless request a field such as tin directly; Eloquent property access decrypts the cast and the spreadsheet mapper emits it. This is a data-exposure boundary failure, not merely an invalid-column validation issue.

Action: make one authoritative module contract validate every requested and persisted column before preview, download, schedule creation, schedule update, and scheduled execution. Reject unknown/unauthorized fields rather than silently humanizing them. Add negative tests proving an export-capable user cannot retrieve tin, sss_no, bank_account_no, or other non-registered fields.

### M011-F02 — Incomplete/high: scheduled exports do not enforce the same module capability boundary

Priority: **P1**  
Scope: **medium**  
Recommendation: **separate-recommended**

The scheduled-export routes require admin.scheduled_exports.view (api/app/Modules/Admin/routes.php:200-217), but ScheduledExportController::validatePayload() only checks that the module exists in the column registry and that columns are strings (api/app/Common/Controllers/ScheduledExportController.php:127-150). It does not call the module-specific permission mapping used by ExportController (api/app/Common/Controllers/ExportController.php:121-146). The due runner later builds the saved module/columns without any acting-user capability check (api/app/Console/Commands/RunDueScheduledExports.php:125-145).

The seeded roles currently give the scheduled-export permission to system administrators through the wildcard role (api/database/seeders/RolePermissionSeeder.php:449-453), but the missing server-side invariant still permits a custom role or permission override to schedule a module it cannot export directly. It also compounds M011-F01 because saved arbitrary columns are replayed by a background process.

Action: centralize module permission, implementation, and column authorization; validate it at create/update and revalidate the stored contract immediately before execution. Define whether recipients may include only the owner or approved organizational addresses, and audit denied or changed schedules.

### M011-F03 — Broken: production export registry and runner advertise more modules than they implement

Priority: **P1**  
Scope: **medium**  
Recommendation: **separate-recommended**

The controller maps permissions for payroll, inventory, and accounting export modules (api/app/Common/Controllers/ExportController.php:132-146), and the inventory stock-level page opens a ColumnSelectorModal for inventory.valuation (spa/src/pages/inventory/stock-levels/index.tsx:79-119). Production boot, however, registers only the employee columns (api/app/Providers/AppServiceProvider.php:187-190), while ExportRunner::MAP contains only hr.employees (api/app/Common/Services/Export/ExportRunner.php:19-36).

Consequently the inventory UI requests a module that is not registered in a normal production process and is rejected as unknown; if a column registration is added without adding the runner class, the next boundary throws No export class registered. The existing scheduled execution test intentionally demonstrates that missing-class failure (api/tests/Feature/Infrastructure/ScheduledExportExecutionTest.php:17-30), but there is no valid production implementation test for the other advertised modules.

Action: either implement and register each advertised module end-to-end, or remove unsupported module keys and UI affordances until their class, columns, permission, filters, and tests exist. A single authoritative catalog should make a module impossible to advertise without an implementation.

### M011-F04 — Missing: the scheduled-export creation flow is absent from the SPA

Priority: **P1**  
Scope: **medium**  
Recommendation: **separate-recommended**

The API client exposes scheduledExportsApi.create() (spa/src/api/exports.ts:75-100), but the scheduled-export page only queries, toggles, archives, and restores rows (spa/src/pages/admin/scheduled-exports/index.tsx:41-84,160-227). No SPA caller of scheduledExportsApi.create exists, and the empty state promises a schedule flow that the page does not provide (spa/src/pages/admin/scheduled-exports/index.tsx:212-216). The HR page exposes only a hand-export button and describes scheduling as a capability without connecting a create form (spa/src/pages/hr/employees/index.tsx:265-279).

Action: add a create/edit flow that reuses the authoritative column selector, carries current filters deliberately, validates recipients/frequency/time, shows next-run and processing/error state, and has an authenticated browser test for create → list → pause/archive → restore.

### M011-F05 — Incomplete: official PDF generation bypasses the central vault and renderer contract

Priority: **P1**  
Scope: **large**  
Recommendation: **separate-recommended**

The vault explicitly claims to be the central path for every system-generated PDF and calls direct Pdf::loadView()->stream() a code-review red flag (api/app/Common/Services/DocumentVaultService.php:19-27). Payslips follow that contract through PdfRenderService and DocumentVaultService (api/app/Modules/Payroll/Services/PayslipPdfService.php:15-25,60-77). Several official documents do not: Accounting streams bills, invoices, journal entries, statements, and purchase orders directly (api/app/Modules/Accounting/Services/PdfService.php:35-122); Purchasing has direct purchase-order/request renderers (api/app/Modules/Purchasing/Services/PurchaseOrderPdfService.php:32-43, api/app/Modules/Purchasing/Services/PurchaseRequestPdfService.php:39-51); Quality CoCs stream directly (api/app/Modules/Quality/Services/CoCService.php:39-63); and Supply Chain Impex documents render directly (api/app/Modules/SupplyChain/Services/ImpexDocumentService.php:27-81). Bulk PDFs and CRM 8D reports also bypass the vault (api/app/Common/Services/BulkPdfService.php:55-64, api/app/Modules/CRM/Controllers/ComplaintController.php:127-145).

This means those documents do not consistently receive a documents audit row, private-vault lifecycle, central download authorization, checksum, or common metadata. Self-service personal certificates are an explicit documented exception and should remain a deliberate separate policy (api/app/Modules/HR/Services/SelfServiceDocumentService.php:15-24); they do not explain the company-record bypasses.

Action: inventory every official PDF type, route each company record through the renderer/vault with its owning entity and document type, preserve intentional self-service streaming as an explicit exception, and add one access/audit/download test per document family.

### M011-F06 — Incomplete: the central document list is not wired to an entity-scoped product surface

Priority: **P2**  
Scope: **medium**  
Recommendation: **separate-recommended**

DocumentList describes an entity-scoped endpoint but defaults to /documents (spa/src/components/documents/DocumentList.tsx:21-45). The only central index endpoint is admin/audit-log gated and filters by document type/entity type, not an entity ID (api/app/Common/Controllers/DocumentController.php:27-52). No current SPA consumer of DocumentList was found, so generated company documents are not surfaced from a normal detail page even though the component offers view/download actions. The separate API client also still says URLs are absolute while the resource intentionally emits relative proxy paths (spa/src/api/documents.ts:1-7, api/app/Common/Resources/DocumentResource.php:37-42).

Action: provide canonical entity-scoped list endpoints or a guarded query contract, mount the component on the intended detail pages, and correct the stale client comment. Add a permission-negative test so an entity list cannot become an admin-document enumeration endpoint.

### M011-F07 — Operational risk: exports and vault downloads are unbounded in memory

Priority: **P2**  
Scope: **medium**  
Recommendation: **separate-recommended**

EmployeeMasterExport calls get() for the entire employee result set (api/app/Modules/HR/Exports/EmployeeMasterExport.php:28-43). SpreadsheetExportService builds a complete PhpSpreadsheet workbook, loops through the complete collection, writes a temporary file, then reads the entire file back into a string (api/app/Common/Services/Export/SpreadsheetExportService.php:20-49,51-83). The scheduled runner retains those bytes and queues a base64 copy in the mailable (api/app/Console/Commands/RunDueScheduledExports.php:137-155, api/app/Common/Mail/ScheduledExportMail.php:29-38). Vault HTTP delivery likewise reads the entire blob before printing it (api/app/Common/Services/DocumentVaultService.php:191-229).

Action: define row/byte limits and timeout policy, use chunked/streaming or disk-backed generation where practical, attach queued files by durable private path rather than embedding large binary payloads, and emit measurable failure reasons for over-limit jobs.

### M011-F08 — Missing: no document/blob retention or orphan-reconciliation path was found

Priority: **P2**  
Scope: **medium**  
Recommendation: **separate-recommended**

Vault deletion removes the row and blob after commit, and regeneration removes the prior blob after the replacement transaction (api/app/Common/Services/DocumentVaultService.php:99-179). The repository has no scheduled command, policy, or documented reconciliation path for old documents rows/blobs, soft-deleted historical versions, or orphaned files; the scheduler only runs scheduled exports (api/routes/console.php:200-206). The scheduled-export migration has rollback methods and execution fields, but no retention policy (api/database/migrations/0124_create_scheduled_exports_table.php:18-58, api/database/migrations/2026_08_11_150000_add_execution_tracking_to_scheduled_exports.php:18-43).

Action: choose retention by document type and legal/audit requirement, add a dry-run/reconciling command with metrics and safe deletion, and document how soft-deleted audit rows differ from physical blob retention.

### M011-F09 — Missing: negative and production-like coverage does not match the risk surface

Priority: **P1**  
Scope: **medium**  
Recommendation: **separate-recommended**

The document controller tests cover authentication, invoice permission, view/download disposition, and confidential cache headers, but not central index/show/destroy, owner-only payslip access, missing blobs, or the strict owner-ID comparison (api/tests/Feature/Documents/DocumentControllerTest.php:18-79). Vault tests cover storage, checksum, confidentiality, regeneration, and entity listing, but not download failure/reconciliation (api/tests/Feature/Documents/DocumentVaultServiceTest.php:20-88). Scheduled execution tests cover only failure lease release and a live lease (api/tests/Feature/Infrastructure/ScheduledExportExecutionTest.php:17-48); they do not cover successful queueing/next-run updates, controller CRUD, arbitrary columns, or module capability checks. The only related browser test verifies that the HR column selector renders mocked choices (spa/e2e/ux-hardening-visual.spec.ts:220-241), not an authenticated download, schedule creation, inventory export, or vault document flow.

Action: add negative security tests first (unknown columns, sensitive fields, wrong module permission, owner mismatch), then successful schedule/document flows, missing-blob behavior, queue failure semantics, and authenticated browser coverage against a running API/SPA.

### M011-F10 — Hardening: Dompdf runs PHP and JavaScript features that are not required by the module contract

Priority: **P2**  
Scope: **small**  
Recommendation: **same-session only after the contract review**

The shared Dompdf configuration enables PHP and JavaScript while remote loading is disabled (api/config/dompdf.php:62-68). This is not a demonstrated exploit because the templates and data paths still need a template-safety review, but it weakens defense-in-depth for a renderer handling employee, payroll, accounting, and supplier data.

Action: disable both features unless a documented template requires them, then add a renderer configuration assertion and review all PDF inputs for unescaped user-controlled HTML.

## Production-audit assessment

### Blockers / high-value risks

1. M011-F01 permits an ordinary HR export permission to request encrypted government-ID or bank fields outside the declared export registry.
2. M011-F02 lets scheduled configurations cross the direct-export capability boundary and replays unvalidated saved columns in a background process.
3. M011-F03 leaves the inventory export affordance without a production registry/runner implementation.
4. M011-F05 means official company PDFs do not consistently have the vault’s audit, authorization, checksum, and private-lifecycle guarantees.

### Evidence still missing

- A negative API test demonstrating that columns=tin is rejected for an hr.employees.export user and that stored scheduled columns are revalidated.
- Successful scheduled-export controller and runner tests, including queue acceptance, next-run advancement, mailable failure, and owner/capability enforcement.
- Authenticated browser/API flows for HR and inventory exports, schedule creation, and entity-scoped document view/download.
- Production-like PDF generation/access coverage for Accounting, Purchasing, Quality, Supply Chain, CRM, Bulk PDF, and the intentional self-service exception.
- Large-export and large-document resource tests, retention/orphan reconciliation, and migration/deployment rollback rehearsal.

### Next action

Do not promote M011 as complete. Execute the action plan in a separate hardening session, beginning with the authoritative export contract and sensitive-column tests, then resolve the unsupported module/UI paths and centralize official PDF lifecycle before adding the broader performance and retention work.

# Audit: maintenance — 2026-09-06

## Summary

The Maintenance module is internally disciplined: a single authoritative state machine, lock-then-recheck idempotency on every WO-creation path (per-schedule, per-machine predictive), race-tested completion/recompute/cost accumulation, careful polymorphic HashID decoding, and a durable outbox handoff for the daily preventive sweep. Its 30-test filter passes clean (95 assertions, ~28s). The defects are concentrated at the **completion seams** — exactly where this audit was pointed. MRP-02 is confirmed from this side: MWO completion resets a mold's shot count but never flips its status back to `available`, stranding it in `maintenance` forever. Worse, the same class of break hits machines: MWO start/complete/cancel write `machines.status` with raw `forceFill` and never dispatch `MachineStatusChanged`, so Production's restoration listener never closes open `machine_downtimes` rows, the live dashboard never sees maintenance transitions, and the reserved `machine_downtimes.maintenance_order_id` link was never wired by anyone — MWO downtime data is invisible to OEE and to the module's own downtime analytics. Secondary: asset-linked maintenance is entirely absent (`assets.under_maintenance` is written by nobody), predictive-WO dedup is broken by a case-sensitive LIKE (dormant since the condition-reading UI was scope-cut), molds under corrective MWO stay schedulable, and in-progress MWOs cannot be reassigned.

### MT-01 — Mold never restored to `available` after MWO completion (High, Broken process)

Confirmed from the owning side of the seam. `MoldService::incrementShots()` flips a mold to `MoldStatus::Maintenance` the moment `current_shot_count >= max_shots_before_maintenance` (api/app/Modules/MRP/Services/MoldService.php:121) and nothing in MRP ever flips it back (only create/retire write status otherwise). `MaintenanceWorkOrderService::complete()` owns the mold completion branch — it locks the mold, resets `current_shot_count` to 0, stamps `last_maintenance_at`, bumps `maintenance_count`, accumulates `total_maintenance_cost` and writes `MoldHistory::MaintenanceCompleted` (lines 239-264) — but never touches `status`. Result: every mold that reaches its shot ceiling is permanently `maintenance` after its first PM cycle, invisible to `scopeAvailable()` and to capacity planning. **Where the fix lives: here, in `complete()`** — it already holds the lock and owns the reset; MRP has no MWO-completion event to listen for (none exists, see MT-02/MT-03 pattern). Restore to `available` unless the mold is `retired`/`decommissioned`. `MaintenanceDoubleCompleteRaceTest` creates molds with status `in_use` and never asserts post-completion status, which is why this shipped green. The MRP-12 note (dead `resetShotCount()`/`recordMaintenance()`) is the same seam: this branch should ideally call those instead of re-implementing inline, but the status flip is missing from both copies.

### MT-02 — MWO machine-status writes bypass `MachineStatusChanged` (High, Stuck process)

`start()`, `complete()` and `cancel()` each write `machines.status` via `forceFill([...])->save()`. `MachineStatusChanged` is dispatched in exactly one place in the codebase — `MachineService::updateStatus()` (MRP, MachineService.php:109) — and there is no model observer, so maintenance-driven transitions are silent. Three concrete consequences: (1) Production's `HandleMachineBreakdown::handleRestoration` closes open `machine_downtimes` rows only on a `breakdown|maintenance → idle|running` **event**; a machine that entered breakdown (downtime row opened by WO pause), got repaired under an MWO and was set back to `idle` by `complete()` leaves its downtime row open forever — MTTR/availability math then clips an ever-growing interval into every reporting window (DowntimeAnalyticsService.php:283 treats NULL end_time as "now"). (2) The `MachineStatusChanged` broadcast (`ShouldBroadcast`) that drives the live machine board never fires for maintenance transitions — floor dashboards show stale states. (3) Starting an MWO on a `running` machine silently flips it to `maintenance` without the pause side-effects production expects. Fix direction: route MWO status changes through `MachineService::updateStatus()` (or dispatch the event with correct from/to inside the same transaction), not raw forceFill. Cross-module coordination with MRP + Production required.

### MT-03 — MWO↔downtime data seam dead in both directions (High, Gap)

The schema reserved the link and the code documents it, but nobody implemented it: migration 0084 created `machine_downtimes.maintenance_order_id` "reserved for Sprint 8 Task 69" (no FK, never written — grep across api/app finds it only in the MachineDowntime `$fillable`), and migration 0101's header claims corrective MWOs are "auto-linked from machine_downtimes.maintenance_order_id when present". Sprint 8 shipped neither direction: no `planned_maintenance`-category downtime row is ever created by anyone (grep: only the enum and OeeService's plan-time classification read it), so MWO time on a machine is invisible to OEE availability/performance — yet the mobile completion sheet tells the tech the minutes are "booked against OEE" (spa/src/pages/maintenance/mobile/work-order.tsx:370). The `downtime_minutes` captured at completion is write-only: returned by the resource and stored on the row, but consumed by no analytics, no OEE calc, no report (grep confirms). Meanwhile the module's own DowntimeAnalyticsService reads exclusively from `machine_downtimes`, so the maintenance dashboard measures downtime from a table maintenance never writes. Fix: at `start()` open a `planned_maintenance` downtime row tagged with the MWO id; at `complete()`/`cancel()` close it (or reconcile against the tech-entered minutes).

### MT-05 — Predictive dedup defeated by case-sensitive LIKE (Medium, Broken process)

`hasOpenCorrectiveWoForMachine()` filters `description LIKE '%predictive%'` and the under-lock re-check in `createCorrectiveWorkOrder()` repeats the same pattern — but the description written is `'[Predictive] %s — Auto-generated from condition monitoring.'` with a capital P. PostgreSQL `LIKE` is case-sensitive, so neither check ever matches an existing row: the one-open-corrective-WO-per-machine guarantee is void, and two breach windows (or a manual reading racing the 02:00 sweep) produce duplicate MWOs. Currently latent — the condition-reading entry routes were scope-cut 2026-08-08 (routes.php:58-84) — but `evaluateAllMachines()` still runs nightly from the preventive job, and the re-enable checklist in routes.php restores exactly this path. Fix is one-word (`ilike`, or match on a dedicated column/type instead of prose — string-matching descriptions is itself the bad practice here); a dedup regression test should accompany it since MobileMaintenanceTest only covers the single-trigger case.

## Cross-module flags

- **mrp (MRP-02)** — confirmed from both sides. The restore belongs in `MaintenanceWorkOrderService::complete()` (MT-01); MRP's `MoldService` also has no restore path, and its dead `resetShotCount()`/`recordMaintenance()` (MRP-12) are the same seam. Fix once, here.
- **mrp** — `MachineService::updateStatus()` is the sole `MachineStatusChanged` emitter; MT-02's fix should route through it (or MRP should expose a transition primitive maintenance can call inside its transaction).
- **production** — `machine_downtimes.maintenance_order_id` is never written by any module (MT-03); Production's downtime-row lifecycle (`HandleMachineBreakdown`) silently depends on an event Maintenance never emits (MT-02). Joint fix.
- **assets** — `AssetStatus::UnderMaintenance` is read by two dashboard widgets and written by nobody; assets can link machines/molds (`linked_type/linked_id`, `molds.asset_id`) but MWO start/complete never syncs asset status (MT-06). Either extend `MaintainableType` or add an asset-status hook keyed off the machine/mold asset link.
- **inventory** — spare-part seam is healthy from this side: issuance delegates to `StockMovementService::move()` (WAC snapshot, lock ordering, spare_part type gate); no negative-stock exposure introduced by Maintenance. MT-11 (no reversal path) is a Maintenance-side gap, not an Inventory defect.

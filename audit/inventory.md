# Audit: inventory — 2026-09-06

## Summary

The inventory ledger core is the strongest subsystem audited so far: every stock mutation funnels through a single method (`StockMovementService::move()`) with deterministic row-lock ordering, optimistic-lock versions, bcmath-only quantity/cost arithmetic, a fail-closed incoming-QC gate on GRN acceptance, quarantine/scrap zone guards on every consumption path, and a lock-then-guard pattern on every lifecycle transition. All 188 tests in `tests/Feature/Inventory` pass (74s). WAC math is correct (4dp half-up, zero-division impossible, issues never touch WAC, reversals re-blend at original cost). The real findings cluster at the edges: (1) the reservation-linked manual issue path is structurally broken (move-before-release, no ownership/status checks, partial-issue reservation leak) though currently unreachable from the SPA; (2) the item-level stock card miscounts transfers as receipts and computes in floats; (3) the GRN→GL valuation rounds 3dp quantities to 2dp, diverging from the stock ledger on fractional receipts; (4) the known 3dp→2dp GRN→PO-line scale mismatch (purchasing's PU-05) is confirmed from this side and can block legitimate GRN rejections; (5) `stock_levels` has no DB-level CHECK constraints; (6) manual issue slips are never validated against the work order's BOM.

### IN-01 — Reservation-linked manual issue path is structurally broken (High, Broken process)

`MaterialIssueService::create()` accepts an optional `material_reservation_id` per line (validated in `StoreMaterialIssueRequest`, decoded and consumed at MaterialIssueService.php:126-134), but every guard that would make it safe is absent:

- **Wrong order — move before release.** The stock movement (line 109) runs *before* the reservation release (line 132). `move()` checks `available = quantity − reserved_quantity`, so on stock that is fully reserved by the very reservation being issued against, `available = 0` and the call throws `InsufficientStockException`. The path cannot fulfil its own purpose in the normal case. Production's internal path does it correctly: `WorkOrderService::issueReservedMaterials()` releases first, then moves (WorkOrderService.php:1014-1029).
- **No ownership check.** The reservation row is loaded by id and immediately marked `Issued` — no check that its `item_id`/`location_id` match the slip line's item/location. Passing a reservation for item A on an issue line for item B marks A's reservation issued and releases reserved stock at B's location.
- **No status check.** There is no `$res->status === ReservationStatus::Reserved` guard (the Draft-cancel branch at line 206 has one; this path doesn't), so the same reservation can be presented twice: each presentation calls `release()`, and the second one silently subtracts reserved quantity belonging to *other* reservations (floored at zero — see IN-08), desynchronising `reserved_quantity` from the sum of live reservation rows.
- **Partial-issue leak.** When `quantity_issued < reservation.quantity`, the reservation is still marked fully `Issued` while only the issued quantity is released — the remainder of `reserved_quantity` stays locked forever (the "leaked reservation permanently locks stock" failure mode).

Mitigating context: the SPA create page never sends `material_reservation_id` (the field exists in the API client type but is not in the form), and no test anywhere references it — so it is currently dead-but-armed API surface for any `inventory.issue.create` holder. Fix: release-then-move ordering, ownership + status + quantity-match guards, or delete the parameter until a real UI needs it.

### IN-02 — 3dp receipt quantities meet a 2dp PO column (Medium, Risk) — confirms purchasing PU-05 from this side

`GrnService` stores GRN lines at decimal(15,3) and accumulates the PO line running total with `bcadd(…, 3)` into `purchase_order_items.quantity_received`, which is decimal(12,2). PostgreSQL rounds on write, so the PO running total can drift ±0.005 per receipt from the sum of GRN lines. Two consequences: the over-receipt `remaining` computation (GrnService.php:197,413) and the three-way match quantity gate both read the rounded figure; and `reversePoReceipt()` (GrnService.php:1203-1207) throws "PO line already below the receipt quantity" when the rounded total falls below this GRN's exact 3dp quantity — i.e. a legitimate rejection of an earlier GRN becomes impossible after later fractional receipts land. Ownership of the fix is Purchasing's (widen the column to (15,3) — note `quantity_accepted` is already decimal(12,3), so the table is internally inconsistent); inventory's write side is correct given the contract it was handed.

### IN-03 — Stock card miscounts transfers at item level (Medium, Broken process)

`StockCardService::direction()` (line 170-179) defaults to `'in'` for movements with both endpoints set — i.e. transfers — when the card is viewed without a location filter. Each in-range transfer is therefore added to the running balance and valued at its unit cost (lines 65-71), inflating the closing balance. Meanwhile `balanceBefore()` (lines 148-160) correctly treats transfers as neither in nor out, so opening balance, in-range rows and closing balance disagree on the same screen. The whole service also runs in floats (balance, value, weighted average). The stock ledger itself is unaffected — this is a report-only defect — but the stock card is the IATF-facing traceability artifact, so a wrong closing balance there is audit-visible.

### IN-04 — GRN GL valuation diverges from the stock ledger on fractional quantities (Medium, Risk)

`GrnGlPostingService::postLocked()` computes the inventory debit as `Money::round2(quantity_accepted) × unit_cost` — rounding the **quantity** to 2dp before multiplying (GrnGlPostingService.php:90-95). `StockMovementService::move()` values the same receipt as `round2(quantity × unit_cost)` with the full 3dp quantity (StockMovementService.php:106,155). For 10.005 kg @ ₱100 the movement total is ₱1,000.50 but the GL debit is ₱1,001.00. Resin receipts in kilograms are exactly the 3dp case, so the GRNI/inventory GL balance and the stock subledger can disagree by a few centavos per fractional line — small per event, cumulative, and it defeats the "GL and inventory agree" invariant the service's own out-of-balance RuntimeException is meant to protect. Cross-module: Accounting consumes the posted lines.

### IN-06 — Manual issue slips are unvalidated against the work order (Medium, Gap)

`work_order_id` on a material issue slip is accepted as a bare reference: no check that the WO exists in a state that consumes materials, that the issued item is on its BOM, or that the quantity relates to the BOM requirement. Combined with the fact that this path never touches reservations, a warehouse user can manually issue a WO's full material list from available slack, and the WO's `start()` will then auto-issue the entire reservation on top — double consumption charged to the same WO (Production's `issueReservedMaterials` bumps `actual_quantity_issued` per reservation regardless of prior manual slips). Cross-module: Production owns the WO state machine, but the inventory-side slip is where a guard (item ∈ WO materials, issued ≤ remaining requirement) belongs.

## Cross-module flags

- **Purchasing (owns fix):** widen `purchase_order_items.quantity_received` to decimal(15,3) — see IN-02 / their PU-05. Also reconcile the internal inconsistency with `quantity_accepted` decimal(12,3).
- **Accounting:** IN-04 GL valuation rounding; verify BillService 3-way match quantity comparison uses the same rounding basis as the PO running total (boundary already drifts per IN-02).
- **Production:** IN-06 — decide whether manual slips may consume WO demand at all; if yes, add BOM validation + reservation linkage; if no, forbid `work_order_id` on manual slips. Production's own reservation lifecycle (reserve at confirm / issue at start / release at cancel) is complete and lock-correct — no leak found on that side.
- **Dashboard:** `inventory.pending_issues` widget counts `MaterialIssueStatus::Draft` slips, a status no code path ever creates → permanently 0 (IN-11).

## Code-reading re-audit — 2026-09-14 (56e0d431)

### Verdict

The current commit includes a real fix for IN-01 and materially expands regression coverage around reservations, HTTP validation, stock-count scope, transfer races, GRN QC, and GRN partial acceptance. The central stock ledger remains well-factored: physical mutations still converge on `StockMovementService::move()`, quantity and WAC writes use BCMath, affected stock rows are locked in deterministic location order, count freezes are enforced, and quarantine/scrap consumption is blocked.

The main unresolved integrity seams are unchanged: the GRN-to-PO quantity scale mismatch, the item stock-card calculation, GRN GL valuation rounding, missing database stock invariants, and unvalidated manual issue-to-work-order semantics. Four additional current-source findings are recorded below: incomplete stock counts can be closed, blocked/inactive locations are not enforced on several movement paths, two inventory resources expose raw integer IDs, and receiving may override PO unit cost without an evidenced approval/reconciliation gate.

No application code, migration, test, registry, or roadmap was changed by this re-audit. Only this section was appended to `audit/inventory.md`.

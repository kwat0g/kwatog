# Audit: quality — 2026-09-06

## Summary

Quality is the strongest chain-touchpoint subsystem audited so far. All four touchpoints are real and fail closed: incoming QC gates GRN acceptance (`GrnService::assertQcGate` — missing inspections fail closed, archived items cannot waive QC), outgoing QC is the ONLY way to create a delivery (output-bound passed inspection, quantity reserved row-level, legacy inspections refused), every failed inspection auto-opens an NCR inside the completion transaction, and CoC issuance re-verifies stored measurement evidence instead of trusting `status=passed`. Tolerance math is centralized (two identical `evaluate()` implementations, inclusive bounds, no re-implementations outside Quality), the AQL table matches ANSI Z1.4 AQL 0.65 Level II with correct arrow-down collapse to code G, terminal inspection/NCR states are lock-then-guard immutable, and the 8D-escalation lesson is fully applied (`ncr:escalate` exits FAILURE with a separated `failed` bucket; durable `ncr_escalation_deliveries`/`ncr_effectiveness_notifications` idempotency ledgers, migration 0478). All 246 quality-adjacent tests pass (821 assertions, 120s). Findings are edge gaps, not holes: complaint-sourced NCRs structurally never spawn replacement/rework WOs; the single-screen receive-with-QC verdict path is incompatible with tolerance-based quality plans; a spec-less product's outgoing fallback draft is a permanent dead end; in-process QC is advisory-only with no between-operation sampling; and one permission covers the entire inspection lifecycle (no segregation). No path found to ship nonconforming product or issue a false CoC.

### QC-01 — Complaint-sourced NCRs never spawn replacement/rework WOs (Medium, Gap) — verified & characterized

`NcrService::close()` creates a replacement WO (disposition=scrap) or rework WO (disposition=rework) only when `$locked->inspection_id && $locked->product_id && $locked->affected_quantity > 0` **and** the linked inspection's stage is `Outgoing` (NcrService.php:318-357). CRM's `ComplaintService` creates complaint NCRs with `complaint_id` set and `inspection_id` null (ComplaintService.php:145-153 and the retry path at 284-292), so the guard is structurally false for them — even with product, quantity and a scrap disposition. Net effect: outgoing-QC scrap is automatically replenished, while customer-complaint scrap (defective parts that already reached the customer) relies on manual planning/8D follow-up; the 8D listener (`AutoSpawn8DOnNcrRecurrence`) covers the CRM side but nothing creates production demand. Characterization: this is a design seam, not an accident — the replacement logic is keyed to "re-create lost output of an inspected batch", and complaint NCRs have no batch. Whether Chain 1 requires complaint-driven replacement WOs (linked to the original SO for re-delivery) is a product decision; if yes, the fix is a complaint→SO-line resolution in `close()`, effort M.

### QC-03 — Single-screen receive-with-QC breaks on plan-based GRNs (Medium, Stuck process) — cross-flag Inventory

`GrnService::receiveWithQc()` applies the operator's terminal verdict to every existing incoming inspection via `fastCompleteInspection()`, which patches `['is_pass' => $passed]` on all measurement rows and calls `recordMeasurements()` (GrnService.php:1326-1340). For any row with a tolerance band (every dimensional plan parameter), `recordMeasurements()` enforces "evidence-bearing parameter: no verdict without a reading" and throws (InspectionService.php:485-496). Since `TriggerIncomingQC` creates plan-based inspections synchronously at GRN creation, any GRN whose item has a quality plan with dimensional parameters (the seeded test case is moisture 0–0.2%) cannot be passed *or failed* from the single screen — the whole receipt transaction rolls back with a technical message. The data-safe path (receive as pending_qc, record actual measurements on the inspection page, complete) works and is the more IATF-correct outcome, but the receiving screen's verdict control silently promises something it cannot deliver for the most quality-controlled items. Options: route plan-based GRNs away from the single-screen verdict, or have `fastCompleteInspection` detect tolerance rows and refuse with an operator-facing "record measurements on the inspection" error before touching the transaction.

### QC-04 — Spec-less outgoing fallback draft is a dead end (Medium, Stuck process)

`TriggerOutgoingQC` catches the "no active inspection spec" BusinessRuleException and falls back to `Inspection::firstOrCreate` with **no measurement scaffold** (no `insertScaffoldRows`). That draft can never complete (`complete()` requires ≥1 measurement row; `recordMeasurements` can only patch existing rows), and because the idempotency guard is the row's mere existence, adding the spec later never re-triggers creation for that output batch. The WO's goods then cannot reach a delivery until someone manually cancels the dead draft and manually creates a proper inspection. Recommend: fail the handoff durably (chain-listener `manual_required` outcome, as TriggerIncomingQC does) instead of parking an uncompletable draft, or re-check scaffold presence on replay.

## Cross-module flags

- **Inventory (seam):** QC-03 lives in `GrnService::fastCompleteInspection()` — fix belongs to Inventory with Quality contract preserved. Also: cancelled incoming inspections waive the GRN QC gate by design (F-12, GrnService.php:736-750) — Inventory may want an audit notification when a GRN is accepted with only cancelled (never passed) inspections.
- **Production:** QC-05 — no in-process gate on `WorkOrderService::complete()` and no inspection hook in `WorkOrderOutputService::record()`; between-operation sampling is not modeled at all.
- **CRM:** QC-01 — decide whether complaint-scrap NCRs should create replacement demand; if yes, `NcrService::close()` needs a complaint→SO resolution path.
- **SupplyChain:** QC-06 — CoC attach-on-confirm is best-effort; consider blocking confirm (or a recovery ledger) when the delivery has inspection-linked items but zero `coc` proofs after the attach attempt.
- **Docs:** QC-08 — SCHEMA.md QUALITY section contradicts the enum law and the real schema.
